0.记住：与我交流时始终使用 ASD-STE100 简化技术风格的中文
1.项目开发的最核心宗旨，在满足用户要求的前提下，写出最简单、最小、最容易读懂的项目。
2.每个类、函数只做一件清楚的事。 单个实现保持简单，需要扩展时再提供不同实现
3.优先组合，而不是堆叠复杂框架。 入口代码只负责挑选组件并把它们组合起来运行。
4.尽量减少不必要的中间变量。 如果一个表达式只使用一次，优先直接传入函数。
5.避免过度封装。 避免没有明确收益的抽象
6.不要提前设计未来可能用到的功能。 只实现当前明确需要的需求。
7.不要擅自扩大修改范围。 用户没要求改的模块、README、配置、接口，不要顺手修改。
8.保持现有接口稳定。 如果修改 protocol、interface、函数签名，必须同步检查所有实现和调用方。
9.除非明确要求，否则不要捕获异常。
10.代码注释尽量少。 只解释真正难懂的逻辑，不要给显而易见的代码加注释。代码注释务必使用中文
11.优先让代码本身具有可读性，而不是依赖大量注释解释。
12.使用现代 Python 写法。 使用 Python 3.10+、类型注解，并优先使用内置泛型，如 list[str] 而不是 List[str]。
13.文件路径操作优先使用 pathlib。 不优先使用 os.path 或冗长的 open() 模式。
14.配置数据优先使用 dataclass 管理。
15.模板字符串或复杂提示词模板优先使用 Jinja 等模板工具，不要大量手工字符串拼接。
16.命令行接口使用统一框架管理。 例如 Python 项目中优先使用 typer，不要自己重复造 CLI 参数解析逻辑。
17.测试使用简单、主流的测试框架。 Python 优先 pytest。
18.不要为了方便测试而随意 mock。 除非确实需要隔离外部系统，否则尽量测试真实行为。
19.不要写“为了覆盖率而覆盖率”的测试。 每个测试至少覆盖一个真实可能发生的失败点。测试代码也要保持简洁。
20.修改代码后优先检查逻辑问题，而不是纠结小型样式问题。
21.提交前重点检查三类问题：异常是否会意外发生、逻辑是否前后矛盾、接口修改是否破坏已有实现。
22.Commit 信息描述“为什么改”，而不是机械描述“改了哪几行”。
不同类型修改使用统一 Commit 前缀。 如fix、feat、ref、docs、chore 等。
23.不要自动往 Commit 中加入AI作为共同作者。
24.你不应擅自补充 README、文档、测试、配置或新功能。 除非这些是当前任务明确要求的一部分。
25.遇到错误时优先保留可观察性。 不要为了让程序“看起来能跑”而隐藏错误。
26.尽量保持执行流程线性、透明、容易调试。 少使用隐式状态、魔法行为和难以追踪的控制流。
27.默认选择最小实现。 如果两个方案都能完成需求，优先选择代码更少、依赖更少、状态更少、接口更简单的那个。
28.前端或是可视化功能，尽可能避免用小字进行过度解释，保证简洁，清晰的视觉风格
