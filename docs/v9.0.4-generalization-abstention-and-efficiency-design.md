## 一、V9.0.3 实测复盘：哪些已经过关，哪些必须重修

V9.0.3 在 `.venv` 独立模式（`has_qgis=False`，42 个 GeoPython 与 8 个 Tier B 库）下跑完了 15 题（9 题 GABench + 6 题 GeoBenchX 全新盲测），总峰值花费 `14.1748` 元。结果非常清晰地划分出了“已过关”与“未过关”的边界：

| 维度 | V9.0.3 实测表现 | 结论 |
| :--- | :--- | :--- |
| **空间计算与 `.venv` 泛化** | GeoBenchX 实际可解的 4 题（`333321`, `618282`, `596430`, `551060`）数值 **4/4 精准命中**；GABench 9 题核心计算 **0 崩、0 硬算错**；`esda/libpysal/mapclassify/netCDF4/rasterstats/sklearn` 均真实调用 | **已过关**（5 大空间分析 Skill 架构方向正确） |
| **Skills 描述泛化度** | 第 `32` 题修复 SAVI 确实受益于 `gis-raster-and-imagery/SKILL.md` 里写明了 `SAVI L=0.5` 与 `DN / 10000.0` | **需泛化**：主 `SKILL.md` 应提炼通用第一性原理，具体算例下沉 `references/` |
| **`gis-verification` 触发率** | 15 题中读取次数为 **`0 / 15`**（对比 `gis-cartography` 为 `15 / 15`） | **未过关**：缺少系统提示与事件驱动触发点 |
| **局部代理与主动合议澄清** | 2 道真实缺数据的 GeoBenchX 题（`304935` 非洲大湖用水、`768309` 南亚洪泛区人口）**`0 / 2` 主动向用户澄清（`needs_input`）或止损（`blocked`）**，全用弱局部代理硬凑 | **未过关**：缺乏侦察后主动找用户“合议确认”的引导，也缺少防止矫枉过正（误拒可解题）的成对评估 |
| **慢脚本超时与尾部空转** | `GAB-09` 前 3 次脚本分别自设 `600s/420s/240s` 超时白耗 21 分钟；`GAB-05`/`24` 在核心成果完成后于末尾反复改图耗尽轮次/预算；`GBX-596430` 恰在第 50 轮交卷被误杀 | **未过关**：超时签名未归并、无“成功态原地空转”感知、评测仍残留死板 `max_calls` 切刀 |

### 本版明确边界（Scope Guard）
1. **本版不做 `gis-cartography` 制图专项改造**（留待下一版本集中重修制图并统一视觉评测）。
2. **保留并强化 V9.0.3 的零常态开销安全气囊**（`detect_spatial_anomalies` + `Confirm-Once` 机制本身无害且必要，本次只补齐它的盲区，不引入老 DAG 式重型调度器）。

## 二、模块 A：空间 Skills 泛化重构与 `gis-verification` 主动触发

### A.1 五大空间分析 Skill 去“题型过拟合”重构
当前 5 大空间分析 Skill（`gis-data-io-and-staging`、`gis-vector-and-network`、`gis-raster-and-imagery`、`gis-terrain-and-hydrology`、`gis-spatial-statistics`）的目录划分和按需加载均已验证有效，但部分 `SKILL.md` 正文包含了过于贴近单题的写法。

**重构原则**：
- **`SKILL.md`（常驻/首读层，≤ 40 行）**：只写**跨数据集可迁移的物理/几何/统计第一性原理**与通用检查动作，不绑死某个特定传感器或特定公式常数。
  - 例如 `gis-raster-and-imagery/SKILL.md`：将“SAVI `L=0.5` 与 `DN / 10000.0`”泛化为**“量纲敏感型指标检查原则”**：凡涉及含加性常数、绝对阈值或物理量纲换算的栅格运算，必须先核验 `dtype`、`scale`/`offset` 与数值量级；区分“乘法尺度不变比值”与“依赖物理标度的绝对指标”，缺失定标元数据时先确认或显式披露假设并做尺度无关指标交叉验证。
  - 具体算例（如 `SAVI/EVI`、Sentinel-2/PlanetScope 常见 `1e-4` 标度）保留在 `references/raster-imagery.md` 与 `scripts/raster_align_index.py` 中，作为按需展开的参考资料。
- 同理检查其余 4 个空间分析 `SKILL.md`，确保正文聚焦通用方法论（如“大几何复杂度先小样本测速再分块/栅格化”、“点面聚合守恒与权重孤岛审计”）。

### A.2 解决 `gis-verification` 读取率为 `0 / 15` 的双通道触发设计
分析原因：`gis-cartography` 在 `system.j2` 第 11 行被直接点名，因此 15/15 必读；而 `gis-verification` 仅列在底部清单中，模型在自觉“代码没报错”时不会主动去读。

**低成本双通道解法**：
1. **系统提示显式锚定（`gis_agent/prompts/system.j2`）**：
   - 将原本只点名 `gis-cartography` 的执行引导补充对等句：在**数据覆盖/口径存疑、执行连续受阻、产物出现异常告警或提交关键数值结论前**，读取 `gis-verification` 核对止损边界与独立验证模式。
2. **运行时按事件注入极短 `verification_hint`（零常态 Token 开销）**：
   - 在 `gis_agent/agent.py` 中，**仅当以下 3 类客观事件之一发生时**，才在工具返回体中附加一句单行提示（正常顺利执行时不注入）：
     - `outputs[].anomalies` 含 `warning`/`fatal` 或 `UNSCALED_HIGH_DN`；
     - `stagnation_alert` 触发（连续失败或连续超时）；
     - 首次调用 `finish_task` 被计划清单门控或 L2 异常门控拦下。
   - 提示文本示例：`"建议先读取 gis-verification/SKILL.md 核对异常排查、独立复算或诚实止损标准。"`

## 三、模块 B：以“主动合议与澄清（`needs_input`）”为核心的可行性契约与防误拒约束

### B.1 为什么头部 Coding Agent 更会主动找人合议、而不是瞎凑或一刀切拒绝？
本轮 `TASK_250309_135125_304935`（非洲大湖用水）和 `TASK_250309_135125_768309`（南亚洪泛区人口等值线）暴露的不是“不会算”，而是**“讨好型硬凑惯性”与工具语义错位**：
1. 目前 `needs_input` 和 `blocked` 都挂在 `finish_task` 下，模型潜意识把 `finish_task` 当成“干完活交卷的工具”，因此即使目录只有残缺代理数据，也会先动手写重型脚本硬做一版再在末尾写免责声明。
2. **重要设计警告——不能把“过度执行”修成“过度拒答”**：在真实交互中，用户最希望看到的是 Agent 发现数据缺口或口径分歧时，**主动找你“合议确认”**（补充缺失数据、确认替代口径或降级研究范围，然后接着干完），而不是动不动直接甩一句 `blocked` 拒答。单纯靠严厉话术把 `blocked` 拒答率拉高，会误杀原本可以合理近似或通过澄清解决的任务（如 `GAB-10` 推导近似边界、`GBX-551060` 人口数折算密度），反而降低实用性。

### B.2 V9.0.4 设计：侦察后三分支决策（执行 / 主动合议 `needs_input` / 确定性 `blocked`）
不新增复杂状态机，通过 **`system.j2` + `gis-verification/SKILL.md` + `finish_task` Schema 描述微调**，把首轮数据探索后的决策清晰拆为三类：

1. **四维快速体检（在编写第一个重型分析脚本前完成）**：
   - **空间覆盖度**：现有数据是否覆盖题目指定主体区域？（如“南亚” vs 仅覆盖孟加拉国局部）
   - **核心实体与指标**：直接目标字段/现象是否存在？（如“多年洪泛风险区” vs “单场 8 天洪水快照”）
   - **空间/时间粒度**：数据粒度是否匹配空间格局需求？（如“流域用水格局” vs “粗粒度国家级年总取水量”）
   - **关键业务口径**：是否存在多种互斥定义、敏感阈值或待补充底图？

2. **三分支防误拒边界（明确“什么时候直接做、什么时候找用户合议、什么时候硬止损”）**：
   - **分支 1：正常推进并披露（严禁误拒 / 严禁过度打扰）**
     - 适用场景：核心计算对象与粒度完整，仅缺次要辅助展示层（如 `GAB-10` 具备全部道路/毁林/保护区矢量，仅缺州边界底图，可用包络近似并标明），或可通过严密物理/几何推导直接满足目标（如 `GBX-551060` 将 1 km 人口数除以球面像元面积得人口密度、`GAB-32` 做反射率定标假设 + 免定标交叉验证）。
     - 行动：**直接执行并交付，不弹问题打扰用户**，在交付摘要中标注合法近似边界。
   - **分支 2：主动合议澄清（`finish_task(status="needs_input")` —— 默认首选）**
     - 适用场景：目录存在**局部代理、粗粒度替代或关键口径分歧**（如 `304935` 仅有 7 国年度总取水 WDI 表、`768309` 仅有孟加拉国 1 场 8 天洪水），继续盲跑会偏离用户本意或白烧多轮 Token，但若由用户补充数据或确认降级口径仍可继续。
     - 行动：**停止编写后续重型处理脚本**，调用 `needs_input` 以结构化 `question` 发起 1 次简洁合议，必须包含三要素：
       1. **已核对到的本地数据事实**（有什么、覆盖范围/粒度）；
       2. **识别出的核心缺口及潜在偏差**；
       3. **供用户拍板的明确选项**（例如：“A. 您补充南亚其余国家/多年洪泛区数据后继续；B. 授权我改为仅分析当前覆盖的孟加拉国局部区域并在成图中明确标明事件口径”）。
     - 用户回复后在**原 Session 无缝恢复（`resume`）**，保留首轮已探查的全部上下文继续完成任务。
   - **分支 3：确定性硬止损（`finish_task(status="blocked")` —— 审慎使用）**
     - 适用场景：完全缺失目标主体数据且不存在任何有效局部/替代切入点（如 `TASK_138450` 既无中国城市边界也无历史建成区，却要求算城市蔓延率），或用户明确要求只基于严格原始全集不允许任何替代。

3. **`finish_task` 工具描述强化（`gis_agent/tools/planning.py`）**：
   - 明确界定 `needs_input` 是**“任务前/中期的联合决策与澄清检查点”**，而非失败收尾；鼓励模型在首轮数据探测发现局部代理或重大歧义后立即发起合议，在减少无效 Token 浪费的同时，避免用 `blocked` 一刀切误拒可澄清或可合理近似的任务。

## 四、模块 C：执行效率提升与“超时 / 原地空转”智能感知

### C.1 解决 `GAB-09` 连续 3 次盲目超时（1261 秒浪费）
**病因**：`run_python_script` 允许模型随手填 `timeout_sec=600/900`，且 `_failure_signature` 把脚本文件名拼进了错误签名，导致模型换个文件名（`02_buffer.py` -> `02a_profile.py` -> `02b_time.py`）连踩 3 次超时却完全没有触发 `stagnation_alert`。

**改动设计**：
1. **超时参数分层收紧（`gis_agent/tools/qgis_python.py`）**：
   - 默认 `timeout_sec` 设为 **`120` 秒**，常规推荐上限 **`300` 秒**，硬上限由 `3600` 秒收紧至 **`600` 秒**（单次探索/原型脚本在描述中明示建议 `60~120s`，逼迫算法尽快暴露复杂度瓶颈）。
2. **超时失败跨文件名归并（`gis_agent/agent.py`）**：
   - 在 `_failure_signature()` 中，若 `payload.get("timed_out") is True`，统一归并签名为 `f"{tool_name}:TIMEOUT"`（不再区分脚本文件名）。
   - 连续 **2 次** `TIMEOUT` 立即触发 `stagnation_alert(level="warn")`，明确建议：**“禁止继续对全量数据直接重试；请先用 5% 样本或单瓦片做 `<10s` 测速，再改用空间索引分块（Tile+Halo）或栅格化方案”**。
3. **大几何复杂度预警写进通用 Skill（`gis-vector-and-network` & `gis-data-io-and-staging`）**：
   - 当 `inspect_data` 显示矢量要素 `> 5,000` 或文件 `> 10 MB` 时，在执行全局 `buffer` / `unary_union` / `overlay` 前，先用小样本基准测速决定是否直接分块或栅格化，避免先跑一次全量赌运气。

### C.2 解决 `GAB-05` / `GAB-24` 尾部“成功态原地空转（Spinning）”
**病因**：`GAB-05`（32 次 `edit_file`）和 `GAB-24`（11 次 `read_image`）每次工具调用都返回 `ok=True`，所以只盯 `ok=False` 的 `_stagnation_alert` 完全失明。

**改动设计**：
- 在 `gis_agent/agent.py` 新增轻量函数 `_spinning_alert(store, messages_slice)`（纯内存扫描当前 turn 最近消息，零额外 IO/LLM 开销）：
  - **检测模式 1（同脚本高频反复微调）**：最近窗口内，对**同一个脚本路径**连续出现 `>= 4` 次 `edit_file -> run_python_script` 且全部 `ok=True`、上游核心数据产物路径未变。
  - **检测模式 2（高频重复看图微调）**：当前 turn 累计 `read_image >= 5` 次且最近连续 `>= 3` 次工具轮次围绕同一张输出图反复重写/重看。
- **响应方式（只提醒，不硬拦）**：
  - 在工具返回体附带 `efficiency_hint`：`"提示：已对同一脚本/图件连续微调多轮且主产物已生成。如核心数值与可读性已满足要求，请停止低收益样式微调，直接完成必要核查并交付。"`

## 五、模块 D：对齐 `learn-claude-code` 的无轮次上限原则，以测试预算护栏替代死板 `max_calls`

核对 `gis_agent/agent.py`（`Agent.drive()` 的 `while True`）与 `learn-claude-code`（`s01_agent_loop.py` 的 `while True`）可见：**产品内核本身从不限制模型调用轮次**，此前第 50/80 轮被中断（如 `GBX-596430` 恰在第 50 轮调用 `finish_task` 却被标为 `protection_stop`）全部源于 `benchmarks/` 评测器人为注入了 `max_calls=50/80` 切刀。

- **产品生产态（`gis_agent`）**：保持 **完全无限轮次**（`while True` 直到主动交付、用户中止或显式触发止损），依靠高水位上下文压缩（90% 上下文窗口收敛）与 `_spinning_alert` 温和收敛提示防止长任务空转，不设硬性请求次数墙。
- **评测测试器（`benchmarks/geoagentbench/run.py`、`benchmarks/geobenchx_pilot.py`）**：
  - **彻底取消硬性 `max_calls=50/80` 切刀**（支持 `max_calls=0 / None` 表示不限轮次，彻底对齐真实使用场景，避免误杀正常长链任务）；
  - 仅保留测试防烧钱所需的**单题预算上限**（如默认放宽至 `task_budget_cny = 4.0~5.0` 元峰值，折合实际基价约 `2.0~2.5` 元）+ **实验总预算硬上限** + **单题墙钟超时 `1800s`**。

### 6.2 验证与低成本 `AgentAbstain` 成对对照回归方案（拒绝“只看拒答率”）
1. **离线回归（0 元）**：
   - `pytest tests/ -m "not slow and not live"` 全绿；
   - `pytest benchmarks/geoagentbench/test_runner.py` 全绿。
2. **线上成对对照验证（Paired Benchmark，预算 ≤ 6 元，`.venv` 独立模式）**：
   借鉴 `AgentAbstain` 成对评估思想，同时测**“该执行时是否坚决执行（Utility / 零误拒）”**与**“该合议/止损时是否精准提问或停下（Calibration）”**，防止把单纯拒答率拉高误判为进步：
   - **正例组（3 题——必须正常执行且不误弹 `needs_input`/`blocked`）**：
     1. `GAB-10`（缺州行政边界但核心分析层完整，验证合法包络近似不被过度澄清误伤）；
