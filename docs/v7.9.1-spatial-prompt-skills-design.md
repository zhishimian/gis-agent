设计日期：2026-10-30。实施状态：2026-10-31已按修订范围落地，并完成两项真实诊断。下文保留当时的设计、候选片段和验证假设；实际修改及结果见[实施验收](../outputs/v791_20261031_01/report.md)。缓冲12次响应，约6～8次目标尚未达成。新增Skill的行为收益仍未证实。

原设计已完成证据审查。本轮只复读现有方案与相关源码，修订本文，没有重新开展全面审计。运行代码、Prompt、Skill、配置、测试及历史记录保持不变，没有启动QGIS运算、测试或模型API。

当前基线为V7.9.0，仓库HEAD为`2eeae7077424a7c2027a60c2319d0d2373df5064`。V7.9.0迁移修改仍在工作区，HEAD单独不能代表本次基线。设计以本轮核对的工作区文件为准。V7.8审计描述的子Agent、前置动态状态和旧制图协议属于历史实现。Matplotlib / GeoPandas / Rasterio制图路线保持原状。

文中的证据分为：**记录确认**、**源码确认**、**解释候选**、**待验证设计**。某个动作出现在轨迹中，可以确认模型做了什么；它通常不足以证明模型为什么这样做。本文中的代码和提示片段均为候选，不代表已存在或已经运行。

## 1. 结论与第一批范围

V7.9.1首先解决三件事：

1. 让已具备的执行能力容易正确使用。讲清直接工具、脚本内Processing与自定义算法的适用条件；把脚本初始化参考放到真正会被看到的入口。
2. 把Verification Skill从五条原则补成小型风险路由。为公式、身份变化、网络假设和几何模型提供具体取证方法，同时复用现有测量工具。
3. 先用免费离线检查确认执行可靠，再只运行一次500米缓冲回归和一次稍复杂的空间分析微任务。记录文字、知识和执行器的实际变化，首轮不开展A/B/C组合实验。

新增轻量的`gis-spatial-analysis`，与`gis-verification`、`gis-cartography`并列。它负责有效组织空间分析；Verification负责选择证据和判断可信程度；Cartography保持V7.9.0的制图职责。共享QGIS执行参考只维护一份。

分析Skill只新增两份短参考，Verification合并为一份核查参考。第一批不新增模型工具，不把初始化助手注册成新工具。标准单步通常优先直接调用已有算法，复杂组合保留自由Python。简单缓冲连同基本核查争取约6～8次模型响应，这是优化目标，不能通过省略必要检查或设置固定上限达成。

成功标准是未知任务的实际结果更正确、完成更顺畅、代价更低。具体QGIS工具调用率、读取Skill次数和Prompt长度都只作诊断指标。

## 2. 必须先纠正的实测解释

### 2.1 V7.9.0的生命周期问题没有被证实修复

[上轮报告](../outputs/buffer500_map_v790_20261030_01/comparison.md)把交付阶段描述为“将图层处理放入main并释放引用，重新执行返回0”。本轮核对原始调用发现，这句话与实际修改不符：

- M11：分析脚本在写出数据后返回`3221225477`。
- M28：提交`completed`，同时在`unresolved`说明收尾异常及图层命名差异，工具拒绝完成。
- M30：`edit_file`将`app.exitQgis()`替换为刷新stdout/stderr及`os._exit(0)`。
- M31：新脚本返回0；M32再次核对数据并出图；M33完成交付。

证据为[完整Session](../outputs/buffer500_map_v790_20261030_01/sessions/buffer500_map.json)中的M30，以及[最终分析脚本末尾](../outputs/buffer500_map_v790_20261030_01/agent_outputs/buffer500_map/scripts/make_buffer.py)。脚本中的“直接正常退出进程”注释也不准确，`os._exit(0)`绕过了正常清理。

因此，保留两项独立结论：

- [独立数据及图件验收](../outputs/buffer500_map_v790_20261030_01/independent_check.json)有效。GPKG几何、CRS、属性和PNG通过检查。
- QGIS生命周期问题仍未定位。返回0来自退出绕过，不能据此认定对象清理已修好。

本轮按用户范围保留历史文件。后续实施时应先更正`HANDOFF.md`及旧报告中的对应表述，保留修订说明。不能把旧记录改写成模型当时执行了正确清理。

### 2.2 原始轨迹还支持两个更窄的判断

第一，V7.9.0确实有核查。M12生成核查脚本，M13、15因多部件访问失败，M18得到半径、面积、ID和几何事实。不能把“核查执行低效”写成“没有核查”。

第二，本轮不存在已确认的JSON类型失败。M13和M15均为`MultiPolygon.exterior`访问错误。后续设计按这两个实际异常处理。

## 4. 职责边界与渐进加载

```text
System：目标、数据保护、简短选择原则、三个Skill索引和结束边界
  ↓
Tool Description / Schema：调用条件、真实参数、返回、可执行入口
  ↓
按需Skill：Spatial Analysis组织分析 / Verification取得证据 / Cartography制作图件
  ↓
QGIS工具 / Python脚本：执行、测量、日志和真实退出状态
```

| 层面 | 应负责 | 当前应避免的职责混用 |
| --- | --- | --- |
| System | 全局目标、明确的能力边界、按需求选择路径、保护输入和诚实交付 | 放完整初始化程序、算法名单或每步检查清单 |
| Tool Description / Schema | 当前接口的参数、类型、大小写、真实返回和局限；指向准确API参考 | 把完整QGIS可接受写法原样复制进较窄的Schema；遗漏必需前提 |
| Spatial Analysis Skill | 选择执行路线，组织多层数据、几何模型、稳定身份和多步流程 | 复制每个工具的参数说明，代替执行器保证正常退出 |
| Verification Skill | 识别会改变结论的风险，选择现有工具和少量反例，解释覆盖范围 | 重做整条分析，成为每步强制门禁或新增登记协议 |
| Cartography Skill | 保持现有静态地图设计、执行与视觉检查方法 | 承担空间分析初始化或本轮分析优化 |
| 执行器 / 小助手 | 安全传参、固定初始化、文件及日志、退出状态、事实测量 | 决定业务公式、擅自改投影、丢弃多部件、用输出存在覆盖失败 |

当前Skill索引已经从frontmatter生成，正文通过`read_file`按需读取。这实现了文件层面的渐进披露。它没有自动匹配器、强制注入器或Skill执行认证；模型是否读取、是否实际采用，要从行为中观察。

`skills/__init__.py`已扫描`*/SKILL.md`，新增分析Skill无需改Factory、Agent循环或另建注册器。简单单步若已有Schema和说明足够，可以直接执行；复杂组合、陌生接口或实际异常才读取相关正文和参考。三个Skill并列不表示每项任务都加载三个。

## 5. 历史错误与根因对应

### 5.1 缓冲轨迹：不能统一解释为“没先搜工具”

| 记录 | 已确认的行为 | 可以支持的根因 | 仍不能确认的部分 |
| --- | --- | --- | --- |
| 首次缓冲M04～06 | 直接工具首次因目录失败，创建`.keep`后成功 | 输出准备曾缺失；后来已由程序补齐 | 不能据此否定直接调用路线 |
| V7.7主M02～03 | 搜索后直接调用成功，没有登记计划或写核查脚本 | 动态工具发现与调用能够工作 | 精度选择不同，不能把全部费用下降归给提示 |
| V7.9 M03～08 | 先写脚本，缺Processing；改后参数键错误；M07搜索、M08直接成功 | 脚本路径引入了额外设置；准确参数已存在于工具接口 | 动机及换提示后能省多少轮未知 |
| V7.9.0 M02～05 | 先读Cartography Skill、API和矢量例程；M04搜索`native:buffer`；下一轮写分析脚本 | 执行路径选择和参考路由仍有缺口 | 不能声称候选未返回或Registry失效 |
| V7.9.0 M06～11 | 写环境探测脚本、改无实际作用的备用路径，之后补plugins路径；分析收尾崩溃 | 初始化成本交给模型；缺少直接可复用的分析入口 | 崩溃可能涉及全局对象、重复provider或其他原生状态，未确定唯一原因 |

V7.9.0 M04查询还返回`native:bufferbym`。请求明知准确ID却给`limit=2`，第二项对固定距离点缓冲没有用途。已有`limit=1`足以缩小此类结果，不必先建设新搜索系统。

该轮可观察的模型解释把“搜索参数”“脚本内运行同一算法”连接起来。它理解自己在使用QGIS，但没有选择Registry函数。这与“完全不用QGIS、从零实现缓冲”有明显差别。评价路径时应分别统计。

### 5.2 初始化说明存在，但到达位置不合适

当前System第9行说“按Skill的执行说明初始化”。Cartography Skill明确不需要QGIS初始化，并把模型引向绘图参考。真正的分析初始化说明位于另一个Skill的末尾链接中。

E05没有`gis-verification/SKILL.md`或共享`execution.md`的读取调用。可以确认本轮没有通过文件工具读取它们；无法据此推断模型完全没有相关知识。

需要让`run_python_script`的说明直接给出分析参考路径。长期可靠性还可以用小助手减少重复样板代码。单纯把初始化段落复制回System，会让所有问答和纯绘图任务持续承担这段上下文。

### 5.3 MultiPolygon：接口知识、修改范围和检查代价

M13调用`geom.exterior`失败。M14仅把顶点计数那一段改成`poly.exterior`，M15的距离列表仍访问`geom.exterior`，再次失败。M16搜索后才修完另一处。

最终脚本使用`max(parts, key=area)`选择最大部分。本题确实只有一个部分，独立验收确认了这一点；该写法不能直接推广到未知多部件数据，会遗漏小岛或其他区域。

应提供的领域知识是：单个要素也可能保存为MultiPolygon；先确认类型和部分数，按任务处理全部部分及孔洞。普通几何有效性、数量和键检查直接用现有工具，只有需要几何数值证据时才写针对性测量。没必要为每次缓冲重复编写圆面积理论、周长、所有顶点和长报告。

### 5.4 整卷：沿传播链看错误

| 风险 | 直接代码或记录 | 根因分类 | 合适的干预点 |
| --- | --- | --- | --- |
| 指标方向 | `20_task2.py`的说明写人均面积，代码却是`capi = eld / g`，随后归一化、排名 | 题意到表达式的转换失败；缺少实际样本与维度核对 | 第一条公式产生后，排名前核对目标量、单位及一个真实样本 |
| 身份错位 | `50_task5.py`把空间连接输出的`fid`当建筑原身份，再回写另一个文件；17777条赋值中17760条与记录住宅区不相交 | 数据模型误用；旧接口未传递FID警告；缺少空间反例检查 | 连接前固定源ID；连接后检查键基数、遗漏及空间关系 |
| 网络近似 | `30_task3.py`先不带接入点建图，再吸附最近顶点；42个不可达对象使用直线回退，写入同一距离字段 | 方法假设与要求不一致；没有保留结果类型及低成本边界样本 | 建图策略确定时核对接入点、方向、代价；抽查长边中部和不可达样本 |
| 指定CRS偏离 | `common.py`把工作CRS固定为栅格的EPSG:32650，题面要求CGCS2000指定投影 | 简化执行条件覆盖了用户约束 | 目标CRS进入有效要求，核对实际转换与最终交付 |
| 归一化掩盖公式错 | 错误指标仍归一化到0～1，排名和输出可正常生成 | 范围检查不能证明量的定义正确 | 在归一化前核对量纲和数值含义 |
| 数据错误进入制图 | 建筑归属错误继续进入改造筛选和图件 | 检查时机落后于高传播风险 | 关联结果参与分配前检查，发现错误只重算受影响部分 |

公式问题不能全部归因于“不懂人均面积”。源码说明和表达式矛盾，已经提供了发现错误的直接线索。空间关联问题同时涉及接口警告与业务选择，也不适合只增加一句“仔细检查”。

任务三要求以直线连接社区和医院作供需示意，直线绘制本身符合题面。应检查医院选择及道路代价，不能用示意连线长度取代路网距离验收。

整卷也有正例：人口总量基本守恒、邻接人口和候选集合复算一致、50个站点及其距离计算得到支持。脚本内Processing和自定义算法具有真实组合价值，不能为了提高直接工具调用率取消它们。

### 5.5 五类原因的证据强度

- **题意理解或表达转换失败**：公式的文字与代码相反、指定CRS被工作方便性覆盖，有直接证据。
- **缺少接口或专业知识**：MultiPolygon访问、错误API、网络接入策略，有实际错误；模型内部知识掌握程度不可观察。
- **工具未提供事实**：旧FID警告确曾丢失。当前已转发，不能再当未修P0。当前键统计仍不比较两个版本的身份覆盖。
- **执行后检查不足**：错误公式进入排名、错误身份进入分配，缺少阻断传播的有效事实。
- **材料已提供但没有采用**：旧强制工具提示仍出现0次具体调用；本轮分析参考没有被读取。提高可见性与提高执行可靠性需要分别研究。

### 7.6 `integrations/qgis/execution.md`

将现有43行参考改为三个短入口：

1. 直接工具的一条完整调用及真实返回结构。
2. 一条完整的多算法脚本例子，包含局部计算、JSON和清理。初始化采用第10节离线验证选定的入口，采用助手后不再并列两套默认样板。
3. 出错后按traceback、返回码、实际层名定位。直接链接分析Skill的Gotchas，不复制故障表。

三种返回必须明确区分：

直接算法工具：

```json
{"ok": true, "algorithm_id": "native:buffer", "outputs": {"OUTPUT": "<绝对路径>/result.gpkg"}}
```

run_python_script外壳，result由脚本写入：

```json
{"ok": true, "returncode": 0, "result": {"outputs": {"OUTPUT": "<绝对路径>/result.gpkg"}}}
```

脚本内`processing.run()`返回输出字典；其中值也可能是同进程图层对象，不能假定全部都能JSON序列化。写出前转成真实文件路径或普通JSON值。

将“原始大写键”改为“算法定义中的原始参数名和大小写”。QGIS并不要求所有provider都使用同一命名习惯。

关于生命周期：初始化和provider准备放在try保护内；计算函数内部持有图层、要素和writer，返回普通结果后再清理。不要重复添加已由`Processing.initialize()`注册的native provider。本机`Processing.py::initialize()`包含对应注册逻辑，但这只能支持避免重复注册，不能证明它是历史访问冲突的唯一原因。

来源：[QGIS 3.44命令行](https://docs.qgis.org/3.44/en/docs/user_manual/processing/standalone.html)、[Processing Python](https://docs.qgis.org/3.44/en/docs/user_manual/processing/console.html)、[Standalone PyQGIS](https://docs.qgis.org/3.44/en/docs/pyqgis_developer_cookbook/intro.html)。参考只保留本项目需要的差异，其他参数回到本机help。

保持四种状态与现有拒绝条件。description中将`unresolved`的“未知事项”收窄为“影响用户要求成立的未完成或未知事项”。图层叫`result`且用户没有指定层名，通常属于成果说明；实际执行失败仍应解决或如实停止。

候选参数说明：

```text
summary：简短说明成果、实际核查范围和正常限制。
unresolved：尚未满足或无法确认的用户要求。非空时不能使用completed。
历史失败已经用可信方式修复时可结束；绕过清理或仅改成成功描述不算修复。
```

后续接口小改可以让拒绝信息指出`unresolved`非空、缺失路径或未完成计划的具体来源。独立记录这项程序改动，不把其收益归到提示文字。不要新增候选登记协议，也不要把所有历史失败设成永久无法交付。

### 8.2 `gis-spatial-analysis/SKILL.md`候选

```markdown
---
name: gis-spatial-analysis
description: 选择和组合GIS分析能力，组织多图层数据与脚本执行。多步空间处理、批量Processing、自定义逻辑或陌生接口排错时使用。

# 空间分析

先明确目标对象、需要计算的量、输入与输出，以及用户指定的CRS和精度。
参数清楚的独立标准操作通常直接调用已有QGIS工具；已有适用算法时复用当前Schema。
批量、连续处理或共享中间对象时，可以在Python中组合Processing；特殊逻辑可使用PyQGIS、GeoPandas等现有库。
简单操作若工具说明已足够，可直接执行，不为阅读本Skill增加步骤。

按需读取：
- 图层、单位、几何、稳定ID和数据流：[操作范式](references/patterns.md)。
- 初始化、参数、返回和完整例子：[QGIS执行参考](../../integrations/qgis/execution.md)。
- 模块、图层或退出错误：[Gotchas](references/gotchas.md)。

读取真实图层和字段，统一计算所需的CRS与单位，保留源身份。
多步处理沿用已经完成的结果；跨进程中间成果落盘。不要重新探测已知环境或重算未变化的数据。
新公式、身份变化或近似可能改变后续结论时，按Verification Skill选择关键证据。
```

根文件只表达跨工具的选择和数据流。已知算法的参数不放这里，Processing初始化代码也不复制到正文。

### 8.3 `patterns.md`：执行范式

保持以下四个短段落：

1. **能力选择。** 直接工具适合独立标准操作；Python Processing适合共享中间层、批量算法和属性逻辑；PyQGIS适合确有需要的GIS对象操作；GeoPandas/Shapely适合表格连接、矢量计算和几何访问。选择以语义、设置成本及数据规模为依据，不规定统一优先级覆盖所有任务。
2. **数据模型。** 文件、实际图层名和内存对象分开。QGIS URI与GeoPandas的path/layer接口分开。先确认几何类型；单个要素也可能是MultiPolygon。需要遍历时处理所有必要部分和孔洞，不静默丢弃小部分。任务要求代表点时可使用合适算法，并保留原面及源身份。
3. **CRS与量。** 使用实际坐标转换满足计算和交付要求，赋CRS标签不能替代转换。单位米仍需核对投影适用性。栅格数量、密度和权重的聚合含义不同。公式先对齐目标量与单位，再进入归一化和排名。
4. **身份与数据流。** 连接或导出前保留独立源ID，不依赖FID或行顺序回写。明确空间谓词、多重匹配和未匹配的处理；不自动采用最大面积归属。脚本内可共享对象，跨进程用真实文件及实际输出路径交接。路网接入、方向、代价和不可达策略在建图前明确。

每段只给一个必要例子或一个权威链接。没有实际需求时不扩写成GIS教材；检验这些操作是否满足要求的内容留给checks.md。

### 8.4 `gotchas.md`：六个高价值入口

| 触发 | 操作提示 | 证据与边界 |
| --- | --- | --- |
| 缺processing | 从共享执行参考使用已配置启动器、实际plugins路径和初始化顺序 | V7.9与V7.9.0反复出现；不猜安装目录或自行重装依赖 |
| INPUT缺失或参数表示冲突 | 按当前Schema/help核对原名、大小写与类型 | 不把所有provider参数统一转大写，不照抄不适用的CLI字符串 |
| GPKG层找不到 | 使用真实输出映射和层枚举，区分路径、layer和URI | 不按文件名或临时别名猜图层 |
| MultiPolygon没有exterior | 根据真实类型处理parts，检查同一段逻辑中的相关访问 | 两次同类错误有记录；不能以取最大部分充当通用修复 |
| 退出异常或访问冲突 | 保留阶段日志，检查应用、对象与provider生命周期，使用离线最小复现 | 原因尚未唯一定位；os._exit(0)不能认证清理成功 |
| finish_task拒绝 | 查看具体未完成要求和字段；正常命名/近似写summary，真实执行失败继续处理或停止 | 不通过隐藏失败或绕过退出满足形式条件 |

这里不再复制公式与空间归属的核查方法。每条包含现象、正确入口和限制；细节指向共享参考，历史竞赛答案不进入生产Skill。

### 8.6 `checks.md`：一份参考，四类证据

| 风险 | 取得的事实 | 不能单独证明什么 |
| --- | --- | --- |
| 公式和单位 | 原始字段、单位及真实非退化样本；核对原量，区分零分母和缺失；归一化前检查 | 输出范围正常不证明公式方向正确 |
| 身份和空间关系 | 空/重复键、源对象覆盖、匹配基数及少量空间反例 | 键集合相同不证明回写位置正确；intersects不证明最优归属 |
| 几何和数量 | 实际CRS、有效性、空值、范围及必要数值；部分与孔洞按需求检查 | 有效几何不证明业务正确；普通面缓冲不能套单点圆公式 |
| 网络及其他近似 | 接入、方向、代价和不可达数量；挑长边中部、跨分量等边界样本 | 正常样本不证明所有近似成立；供需示意直线长度不等于道路代价 |

已有样例可能全为零或空，不能假定summarize_fields会自动挑出非零记录。必要时针对性取样。既有关系工具只能测source中现存对象，遗漏检查可用少量集合比较；暂不因此新增模型工具。

面向任务记录简短的PASS/FAIL/UNKNOWN及覆盖范围。公式例子使用独立小数据；归属策略由用户要求确定。该参考不保存试卷公式、固定排名阈值或标准答案。

### 8.7 新增分析Skill的必要性与反对意见

**反对意见成立的部分：** 精确ID搜索、参数大小写、输出映射和finish语义，主要通过工具说明就能改善。这些内容不能为了充实Skill再写一遍。初始化的可靠性也必须由实际代码和离线检查支撑。

**仍值得新增的部分：** 多图层任务需要在操作之前组织对象身份、CRS、几何模型及多步数据流。这些是跨工具的执行方法，与验证阶段“凭哪些证据相信结果”不同。把它们放入一个短的分析入口，更容易在写脚本之前发现。

因此采用窄描述、短正文和两份参考，不强制所有分析请求读取。如果真实轨迹表明它只重复工具说明、没有改变有效行为，应删减其正文或把冗余内容归回工具说明；三个目录本身不构成能力收益。

继续复用现有skill_index，不增加自动分类器、强制注入、每步钩子或已加载认证。模型可以直接进入工具说明给出的共享参考，避免先读两个Skill才能找到一个接口。

## 9. 简单任务争取约6～8次响应

### 9.1 减少哪些往返

V7.9.0的M01～18同时包含接入、前置制图资料阅读、搜索、脚本生成、环境探测、初始化修复和几何访问修复。改进目标包括：

- 标准单步用已经存在的具体算法，减少自写初始化及环境探测。
- 已知ID时缩小候选，适用Schema仍在时复用，不为同一操作重新检索。
- 基础字段、键和有效性核查复用现有工具，不为常规核查另写一套程序。
- 简单操作不强制计划、额外报告或证据登记，不提前读取制图正文。
- 对同一原因的多处错误集中定位与修改，避免只改一处后继续碰到相同错误。

### 9.2 一条可能的精简轨迹

| 信息阶段 | 可采用的现有能力 |
| --- | --- |
| 确认输入 | inspect_data，必要时批量读取 |
| 获得准确接口 | search_qgis_tools；已提供Schema时复用 |
| 执行算法 | 具体qgis工具 |
| 轻量核查 | summarize_fields及需要的元信息；独立的只读测量可同轮提交 |
| 结束交付 | 单独finish_task，列实际成果及核查范围 |

这条路径只作示例。读取层信息后才能确定的调用等待相应结果；搜索和未提供的具体工具不能在同一响应中假定可用。

上述阶段加必要的参考或额外数值抽查，争取约6～8次模型响应。五次即正确完成也可接受；超过八次时分析原因，不自动终止或删掉检查。复杂组合仍允许Processing和自由Python，不能为了少几轮拆散合理批处理。

独立评分者核对半径等完整几何事实，Agent本身可按任务风险做轻量核查。评分者的额外计算不算成Agent已经取得的证据，两者在结果中分开记录。

## 10. 执行器与Processing生命周期方案

### 10.1 保留一个自由脚本入口

run_python_script的模型名称、参数和日志契约保持不变。Windows JSON传参、工作目录、项目根路径、结构化结果和真实退出状态继续保留。新分析Skill不改变QGIS环境隔离。

标准算法直接调用不需要模型管理QgsApplication。纯GeoPandas/Shapely和现有Matplotlib绘图进程也不自动初始化QGIS。只在脚本确实使用Processing/PyQGIS时进入对应生命周期。

### 10.2 轻量助手与完整范例怎样选择

候选仍为`integrations/qgis/python_runtime.py`的普通函数：

```python
def run_processing(job: Callable[[], dict[str, Any]]) -> None:
    ...
```

它只负责一次分析进程的初始化、Processing准备、调用局部job、清理及写出普通JSON结果。它作为脚本内的普通函数使用。具体QGIS算法、参数和检查仍由job决定。

job中的图层、迭代器、writer和连接要在清理应用前释放，返回值不能携带QGIS对象。助手不能清除任意全局引用，也不能保证所有插件和驱动都能正常退出；异常traceback可能保留对象引用，同样需要离线定位。

**选择门槛：** 先用免费离线小例程比较完整范例和助手：真实输出是否相同，正常/异常路径是否可观察，是否保持正常清理，模型需要重复生成的样板是否明显减少。通过后优先采用小助手，并在execution.md只展示一条默认脚本入口。完整初始化范例作为诊断材料保留，避免给模型两套同等优先的样板。

如果完整范例已短且稳定，助手没有明确收益，可以只保留范例。如果两条脚本路径都不能可靠清理，应先修执行问题；不要把不稳定入口交给收费模型反复试错。已通过的直接算法和纯Python能力仍可使用。

样板字符数或代码量只能提供潜在Token收益线索。第一轮两项任务没有使用助手时，不能宣称已经实测它更省Token；后续有真实脚本需求时再评价，当前不专门增加一组收费对照。

### 10.3 免费离线定位步骤

后续实施时，使用配置好的同一QGIS启动器，在隔离小目录逐步增加能力：

1. 仅导入PyQGIS，初始化应用并退出，取得无业务对象的基线。
2. 加Processing初始化，核对实际plugins路径和provider，避免重复添加native。
3. 读取小GPKG，将图层、要素和迭代器限定在局部计算函数内，返回后清理应用。
4. 执行一项真实Processing并写GPKG，确保writer和数据连接释放，再清理。
5. 对比发生崩溃的原始版本与局部作用域版本；一次只改变对象持有或初始化条件，记录阶段、returncode、stderr，必要时使用faulthandler辅助定位。

记录要区分“job已返回”“结果已序列化”“工程已清理”“exitQgis已返回”和“进程正常退出”。阶段标记是诊断证据，不能单独保证任意脚本的生命周期正确。若缺少Python traceback，保留原生退出信息，不先宣布唯一原因。

本机Processing.initialize已包含native provider准备，重复注册是需排除的条件；它尚未被证实为历史崩溃的唯一原因。单次不崩溃也不足以证明问题消失。

### 10.4 必要的免费离线验收

| 场景 | 验收重点 |
| --- | --- |
| 正常分析 | 小GPKG读写和结果正确；约定清理阶段完成；子进程最终为0 |
| 真实参数或字段错误 | 保留原始异常及非零状态；部分文件不登记成成功成果 |
| 初始化/清理失败 | 能定位阶段；不通过捕获异常、改返回码或os._exit伪装成功 |
| 对象及文件释放 | job不向外返回QGIS对象；另一个进程可重新读取成果；重复独立启动仍正常 |
| 主链兼容 | JSON特殊字符参数、已有数据检查及会话恢复相关检查无回归；纯绘图不加载新助手 |

正常路径做少量独立进程重复，以覆盖启动和清理。失败路径同时核对日志与退出状态。明确的原生问题未解决时先停在离线定位，不用Prompt作可靠性替代。

### 10.5 Tool Schema和错误反馈的最小改动

保留第7节的高价值修改：准确ID候选、描述与Schema类型一致、实际输出映射、统计/关系工具的边界、finish未完成要求的语义。

可在adapter调用前识别未知参数名，返回允许的键；不要自动把参数改成大写。只为已确认的Processing导入异常附共享参考，其他异常保留原始诊断。finish拒绝时指出具体字段或计划项，继续保留原来的完成检查。

不扩大所有参数联合类型，不新增describe、通用验证器或搜索框架。错误反馈的程序变化独立记录，不能全部算为Prompt收益。

## 12. 第一轮验证：免费离线通过后，仅两项真实任务

### 12.1 总体约束

本轮不执行任何测试。未来实施完成后，先通过第10节的免费离线检查，再依次运行下列任务各一次。

不运行完整竞赛题，不追加A/B/C分组，不因结果不好自动重跑。使用新Session和隔离输出，固定模型实际版本、参数、记忆开关、库环境及输入哈希。保持V7.9.0的Matplotlib通道，本轮两个分析任务均不要求图片。

这样能检查空间分析和基本核查的真实响应成本，避免提前加载制图Skill。交付范围与旧缓冲加PNG实验不同，报告必须注明；不能把费用差全部解释为分析优化收益。

### 12.2 任务一：500米缓冲回归

候选用户输入：

```text
对提供的input.gpkg中的points层生成500米缓冲区，SEGMENTS=32，不融合，
保留id，保存为result.gpkg。输入为EPSG:32650，单位米。
完成必要的轻量核对后交付，保留原始输入，不额外出图或写报告。
```

沿用历史原始点数据副本，核对原始SHA保持一致。题面不指定必须调用哪个内部函数。

验收分为两层：

- **Agent行为与完成度：** 能使用已有准确接口，不无故反复搜索或探测环境；基础检查取得真实事实；交付实际数据。简单任务不增加计划、长报告、证据登记或无关Skill阅读。一般争取约6～8次响应，超过时如实分析，不能压掉必要核查。
- **独立结果检查：** 实际GPKG可读，CRS为EPSG:32650，id及输入属性完整，几何非空有效；固定输入的外环128段、无异常孔洞、范围及半径满足500米，面积符合SEGMENTS=32的多边形近似。原始输入不变。

这个输入是已知回归例，不代表未知任务泛化。Agent可以用现有统计/元信息工具做基础核查，独立评分者另做完整几何验收；两类证据分别记录。精度一致时才比较响应与费用。

若Agent选择Processing脚本，记录具体组合理由、初始化和退出情况；语义等价且可靠的路径仍可通过。单纯增加直接工具调用率不能替代结果正确性。

### 12.3 任务二：多图层关联、字段计算与身份保持

使用小型合成真实格式数据：12栋建筑、3个服务区。面积和人口均为正，字段含义明确。业务building_id、zone_id与FID无关，并打乱行序；包含一个MultiPolygon建筑、一个多匹配建筑和一个区外建筑。各服务区都有唯一归属建筑，避免首次任务同时变成异常数据大集合。

候选用户输入：

```text
使用buildings和zones两层，将每栋建筑按面内代表点归属到覆盖该点的服务区，边界接触计入覆盖。
一个代表点匹配多个区时标记ambiguous，没有匹配时标记unmatched；两类均保留，不参与人口分配。
每个区的人口只在唯一归属的建筑中，按usable_area_m2比例分配，允许估计人口小数。
对参与分配的建筑计算人均可用面积，单位平方米/人。
输出GeoPackage，保留全部原始building_id、原面几何及归属状态；唯一归属项保存zone_id，其余项留空。
返回各区已分配人口及匹配状态的简短统计。保留输入，不要求地图或正式报告。
```

数据中的usable_area_m2是给定业务量，不能偷偷替换为轮廓面积。多部件建筑的各部分安排在同一区内，多匹配建筑完全位于重叠区内，区外建筑完全位于区外。这样可避免不同面内代表点实现产生无关分歧。题面明确覆盖和多匹配规则，生产Skill仍不预设这些业务选择。

验收重点：

1. 全部12个building_id保留，最终建筑层每个ID一条，原属性和几何不因连接而丢失或替换。中间一对多关系允许存在，不能误回写FID。
2. 唯一归属、ambiguous、unmatched符合题面；zone_id和实际空间关系一致；未分配项不伪装成零人口的正常分配。
3. 按真实面积权重分配人口，区内合计与该区目标一致；人均面积方向和单位正确，不先舍入造成明显总量误差。
4. 由评分者基于输入独立计算期望键、关系和数值，按事先固定的小数容差核对，例如人口与人均面积的绝对/相对容差。容差必须与存储精度一致。
5. Agent取得少量关键证据，覆盖身份或空间归属、公式及分配总量；无需重做全套算法或逐行写长核查报告。
6. 允许直接工具、Processing、GeoPandas及自定义代码的合理组合。记录实际路线、工具错误、恢复及费用，不给某种路线额外正确性分。

在未来免费准备阶段固定数据、独立真值、数值容差及简短评分表；它们不提供给受试Agent。运行前只给正常题面和输入，不能把预期匹配ID或答案表混入上下文。

该任务是开发微任务，不能宣称是严格未见留出测试。当前文件工具没有严格访问沙箱，评分材料应在受试身份不可读的位置保存；本版不因此开发新的沙箱框架。

### 12.4 最小记录与判断

两次运行分别保存题面、输入/源码指纹、Session和资产、逐轮usage、缓存hit/miss、输出及思考token、响应数、工具错误、实际脚本、日志、结果和独立评分。费用按当时实际单价核算，说明缓存与重试情况。

分开报告：数据正确性、需求完成度、正常执行/清理、Skill是否读取及实际采用、响应与费用。os._exit绕过不能记为生命周期修复；正确结果也不能据此被改写成几何错误。

第一项成功且离线执行条件保持正常后，才运行第二项。若遇到环境/API阻碍、原生崩溃或重复无进展错误，保留记录并停止后续收费任务，先定位；不静默重启。产品不新增固定总响应上限。

两项任务是工程诊断，无法分离各项改动的因果贡献，也不足以证明稳定性。依据实际失败再决定下一轮微调或少量对照，当前不承诺立即扩展到更多任务。

## 13. 原方案的删除、合并与推迟

| 原建议 | 本次处理 | 原因 |
| --- | --- | --- |
| 仅保留两个Skill | 调整为三个轻量入口 | 分析执行与风险取证分工更清楚，仍复用现有加载器 |
| Verification的quantities、identity、networks、geometry、gotchas五份参考 | 合并、迁移为分析两份参考加验证一份参考 | 操作知识与证据判断各有主要位置，减少查找及重复 |
| 广泛的Spatial Analysis百科 | 不建立 | 无法替代模型常识，也容易增加上下文 |
| 大规模A/B/C、15个微任务、综合G1/H1和重复预算 | 从首轮删除 | 先用必要离线检查及两次真实诊断发现问题 |
| 新增compare_keys及关系工具参数扩展 | 推迟 | 先复用现有工具和必要的小型集合比较，观察真实缺口 |
| filter_expression、geometry_facts、describe及搜索平台 | 继续推迟 | 缺少首轮必须新增的证据，避免工具膨胀 |
| Processing助手 | 保留，先做免费离线定位和准入判断 | 稳定初始化与清理属于运行时责任，不能交给提示兜底 |
| Tool Schema和错误反馈优化 | 保留最小范围 | 实际接口歧义和误导值得直接修正 |
| 默认逐步验证、证据登记、额外报告 | 不引入 | 容易重复V7.7的高开销，核查应围绕真实风险 |
| 制图再设计、多Agent、RAG、工作树 | 不进入本版 | 与本次分析优化无直接依赖，现有制图保持不变 |

保留历史审计和四篇教程作为设计依据，运行时Skill不加载整份研究材料。后续若要研究因果归因或跨模型差异，再根据已取得的任务数据安排必要对照。

## 14. 实施顺序与完成标准

以下步骤均为后续实施计划，本轮没有执行。

1. **固定基线和更正记录。** 保存当前代码与环境指纹；更正生命周期误述，原始Session及成果保持不变。
2. **先定位脚本可靠性。** 按第10节免费离线逐步复现初始化、Processing和退出；选择经验证的完整范例或轻量助手，不发布未经验证的入口。
3. **补工具契约。** 修正Schema说明冲突、参考路径、实际返回及精准错误；保留原接口和有效保护，不增加模型工具。
4. **落实三个Skill的职责。** 新增短分析Skill，精简Verification并合并参考。共享执行说明维护一份，Cartography不重构；现有索引自动发现新目录。
5. **检查最小主链。** 运行与变更相关的免费离线检查，确认参数调用方、失败状态、正常清理及已有会话/执行能力无回归。
6. **依次完成两项真实诊断。** 一次缓冲回归，一次空间关联/计算微任务；不自动复测，不运行整卷或大型分组。
7. **按结果决定下一步。** 优先看正确性和真实完成，再看响应、费用和Skill收益。有具体失败再缩小修改；不能仅因三个Skill均被读取就认定成功。

新增分析Skill能否帮助模型在写程序之前组织数据，是待验证假设。某些问题只需准确的工具说明和运行时修复，就不再向Skill累加文字。若新增入口只有阅读成本，应删减重复内容，而不扩大Skill的触发范围。

本版的工程目标是更顺畅的空间分析：简单任务通常直接执行并做轻量核查，复杂任务可以自由组合可靠能力。约6～8次响应是简单缓冲的优化目标，正常初始化/清理和结果正确性是不可用形式绕过的验收要求。
