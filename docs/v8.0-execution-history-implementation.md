## 2. Session 与回执的关系

Session 仍保存原始调用参数和工具结果。执行历史从这些事实生成；旧 Session 可以直接读取，不补写原文件。

新增回执位于：

```text
sessions/<session>.assets/executions/e000042_00.json
sessions/<session>.assets/executions/e000042_00.traceback.txt
```

ID 来自 assistant 消息序号与该消息的调用位置，避免跨消息重复 tool_call_id 混淆。每个真实调用自动记录；模型不做额外登记。

回执只补时间、调用/消息指纹、有限完成消息和诊断引用。大型工具结果继续使用原资产，脚本和日志继续引用原 python_logs。超过 16000 字符的完成消息不再复制到回执；此时只保存关联指纹，不能保证孤立回执保留完整结果。

成功、失败、正常返回、异常和未知分别表示。查询成功的 `ok=true` 只表示查询完成；实际执行情况看 item.status。succeeded 表示原工具报告成功，不证明 GIS 业务结论正确。

孤立完成回执可以只读查看，状态仍为 unknown/orphan。它不会修补 Session、推进 Checkpoint 或触发工具重放。原 790 检查点版本和严格哈希保护保持。

## 3. 调整设计中的故障策略

原设计提出历史 begin 写失败后停止工具。本次实施将它收紧为分层处理：

| 故障 | 实际行为 |
| --- | --- |
| 关键 Session.started 或结果保存失败 | 原样抛出；不绕过原有安全边界 |
| 辅助回执 begin/complete 写入失败 | 输出 warning 和异常栈，继续原工具/Session 流程 |
| 工具本身抛异常 | 尝试记录 raised，随后原样抛出；回执失败不替换原异常 |
| 只有 started 或进程被强杀 | 只读显示未知，不自动重放 |
| 完成回执与调用、结果或状态冲突 | 查询标 unknown/conflict，保留诊断 |
| 结果资产缺失、哈希不符或越界 | 标 unknown/corrupt，不当作成功 |

理由：回执属于辅助可观测性。原 Session 已负责调用安全。历史目录故障不应降低原 V7 可用性；缺少回执时，完整的 Session 仍能提供真实调用和返回，时间等缺失字段保留 null。

完成回执禁止改写成另一个结果或异常。记录功能不做自动重试。

## 4. GIS 与 Python 的关联边界

### QGIS

内部元信息保存 algorithm_id、参数类型、destination 标识和定义指纹。模型看到的 QGIS Schema 不变。

实际参数来自原调用，输出引用来自真实 outputs。省略参数单独列出，不将当前默认值冒充历史实际值。可识别输入只记录引用，依赖完整性仍是 unknown。

默认不哈希 GIS 数据。位于会话成果目录内的输出记录观察时间、存在性、大小和 mtime，标 stat_only；其他报告路径仅保留引用。文件存在不代表业务正确，文件后来变化也无法据此恢复原版本。

### Python

原脚本仍按原路径运行，cwd 和参数传递不变。历史复用原快照、脚本哈希、stdout/stderr、结构化结果和 request.json。

脚本事实明确标记 `execution_mode=original_path`、`actual_code_identity=not_proven`。快照与原文件前后相同不能排除运行中的瞬时修改。

新执行在完成时记录 request.json 指纹。旧 Session 的 request 引用没有历史指纹时保持 unverified，受限接口拒绝把它当作已验证资源读出；原始调用参数仍能直接查询。

普通 Python 的隐藏文件、数据库或网络依赖没有自动发现，也没有自动缓存资格。

## 5. 真实可用的接口

### Agent 工具

```json
{"query":"fifth.py","tool":"run_python_script","section":"detail","max_characters":8000}
```

调用工具名为 `execution_history`。该调用返回最新匹配执行的原参数、代码摘录、错误、结果、来源与链接。也可以用 execution_id 精确查询。

section 支持：summary、detail、arguments、result、error、links、script、stdout、stderr、request、traceback。详情通过 cursor/next_cursor 分页；列表通过 offset/next_offset 分页。

detail 默认附最多 2000 字符代码和 1500 字符 stderr 摘录。完整代码可以继续读取：

```json
{"execution_id":"e000059_00","section":"script","max_characters":8000}
```

查询按工具、脚本/成果路径、错误与状态过滤。多项匹配时默认选最新项；offset 可选更早的执行。没有固定失败后查询要求。

### CLI

```powershell
python main.py history --session demo --query fifth.py
python main.py history --session demo --execution e000042_00 --section detail
python main.py history --session demo --execution e000042_00 --section stderr
python main.py --session demo
python main.py chat --session demo
```

最后两种聊天写法均保留。history 不创建模型客户端，不初始化 QGIS，也不要求 API Key。目录遵循项目路径配置；归档会话可显式给 --project 和 --output-dir。

### 安全边界

工具不接受任意读取路径。结果资产只允许当前 Session 的 tool_results；资源正文只允许指定会话的 python_logs，或对应执行的异常日志。读取前检查路径范围、文件名和已有哈希。

原始数据路径可以作为检索线索或返回引用，但不会因此读取任意文件正文。CLI 的 --output-dir 是用户显式选择的归档目录，Agent 工具没有该参数。

这不构成对自由 Python 的操作系统沙箱；原有代码执行权限保持。

## 7. 性能实测

同一本机、1000 条小型合成执行，每条有实际 begin/complete 文件回执，默认查询最近 5 项，查询采样 12 次。

| 项目 | 实测 |
| --- | ---: |
| 1000 份回执总大小 | 592335 字节 |
| 平均/最大回执 | 592.335 / 593 字节 |
| begin+complete 中位数 | 18.73 ms |
| begin+complete p95 | 29.45 ms |
| 默认千条查询中位数 | 124.93 ms |
| 默认千条查询 p95 | 196.46 ms |
| 返回 5 项摘要 | 2867 字符 |
| 新工具 Schema 增量 | 235 token |
| 独立进程导入 CLI | 267.90 ms |

tokenizer 为本机缓存的 `deepseek-ai/DeepSeek-V4.1-Flash-1017`。235 是同一计数器下“仅新增 Schema”的请求估算差值，没有模型响应或账单。新 Schema 仍会增加普通请求输入；没有新增响应不等于没有新增 Token。

初测默认千条查询中位数约 1218.67 ms。仅减少路径解析仍未解决，后续改为：默认先从 Session 筛选候选，再核验实际返回项的辅助回执；未配对异常仍读取回执。

默认返回 `matches_scope=session_candidates`，数量表示 Session 匹配候选。返回项会独立核验，冲突项显示 unknown。显式 status 筛选则核验全部相关回执，返回 `matches_scope=verified_records`，不会用未核验的状态筛选结果。

显式全量状态核验仍有较多小文件 I/O，不承诺同样的 200 ms。这里的 p95 用 12 样本最近秩计算，等于本组最大值；受磁盘缓存和系统负载影响，不能当作稳定线上 SLA。

这组微基准使用很小的结果，不代表复杂 QGIS 或长工具结果的最大回执尺寸。大日志按需读取仍需全文件哈希和解码；旧大型 JSON 资产的校验也有 I/O 成本。没有测真实模型 Token 总量或任务费用改善。

## 8. 原有真实失败的只读演示

使用新接口查询 V7.9.3 下午原 Session，找到了：

- execution_id：`e000059_00`。
- 实际脚本：`s05_task1c.py`。
- 状态：failed。
- 原错误：`IndexError`，涉及 `qx[mask]` 的数组维度。
- detail 包含原参数、2000 字符代码摘录、769 字符 stderr 和原工具结果；完整 detail 为两页。
- CLI 的 script 查询一次读回全部 4554 字符代码，next_cursor=null。

原 Session 读取前后 SHA-256 相同。没有执行原脚本或 GIS 业务运算，没有替 Agent 修复答案。

因此，第十步发现第五步脚本有问题时，Agent 现在可以先用一次 execution_history 的 detail 查询取得最小定位资料。需要完整代码时再用已返回 execution_id 读取 script；需要完整日志时读取 stderr/stdout。它无需按消息序号翻整段对话，也无需重新执行第五步。

长代码、长结果可能需要分页；本版不承诺任何历史问题都只用一次调用。

## 9. 能力边界与 V8.1 前置项

V8.0 已提供事实查询和执行记录。它尚未提供局部重放、数据版本回滚、可靠依赖图或自动缓存。

进入 V8.1 前仍需：

1. 明确可复用阶段的本地输入、输出、代码与环境身份。
2. 单独实现受控目录和新修订，保护已有成果。
3. 定位成功后的参数/代码修改、依赖绑定与连续重算。
4. 对完成回执存在但 Session/Checkpoint 落后的窗口进行窄恢复验证。
5. 用少量获准真实任务评价模型是否采用历史，以及完成率、Token 与原生时间净收益。

现有查询只能提供信息。模型仍负责识别专业问题、决定修复方法和选择核查范围。本次不声称自主修复率或真实任务费用已经改善。
