# V8.0：工作树与局部回退详细设计

## 1. 目标与范围

状态：历史详细设计，尚未实施。本文基于 V7.6，包含旧接口。当前候选与实施边界见 [V8 候选需求](v8-candidates.md)。开发前须按 V7 冻结源码重新核对。

本版解决一个具体问题：GIS 流程中间一步出错时，保留有效的上游成果，修正出错步骤，再计算受影响的下游。

最小验收流程为：重投影 → 缓冲 → 叠加。验证发现缓冲距离错误后，Agent 保留已检查的重投影成果，在新分支重新缓冲和叠加。

V8.0 实现单个任务内的顺序执行、分支记录、成果复用和局部修正。每次处理一个分支。分支之间共享上游成果，因此步骤依赖按有向无环图（DAG）记录。

首轮覆盖本地文件、native Processing 算法和依赖明确的 QGIS Python 脚本。大脚本可以登记为一个步骤，回退粒度随脚本边界确定。

本版的成功标准是可靠地完成一次局部修正。自动比较多个方案、分支评分和搜索策略留给后续迭代。

## 2. 与 LangGraph 的结合

### 2.1 两层职责

| 组件 | 本版职责 |
| --- | --- |
| LangGraph | 沿用 model、tools、finish，保存执行位置，继续当前循环 |
| WorkflowRunner | 登记 GIS 步骤，绑定真实调用，核对版本，建立修正分支 |
| Session | 保存用户要求、模型响应、实际工具调用和返回结果 |
| 工作流文件 | 保存步骤输入输出、依赖、版本和分支关系，通过哈希关联 Session |

每个 GIS 步骤仍由现有具体工具执行。例如，LLM 继续调用 qgis_native_buffer，脚本继续通过 run_python_script 运行。工作流工具管理这些调用的执行边界。

现有 StateGraph 的三个节点保持原有结构。GIS 节点作为业务数据保存。这样可以复用当前动态工具搜索、上下文、子任务和交付流程。

### 2.2 本版如何回退

LangGraph 支持从检查点回放和建立分支，回放会重新执行后续节点及其外部调用。见[官方时间旅行说明](https://docs.langchain.com/oss/python/langgraph/use-time-travel)。

当前项目还会核对 Session 与检查点中的 record_hash。V8.0 继续沿用该约束，在当前对话中建立 GIS 分支，并追加修正记录。旧对话、旧步骤和旧文件全部保留。

因此，一次 GIS 回退的过程是：

```text
当前 Agent 读到复核问题
  → 选择需要修正的步骤
  → 建立 GIS 新分支
  → 核对并继承有效步骤引用
  → 在新目录执行修正步骤
  → 重算受影响的下游
  → 重新提交成果复核
```

检查点负责继续程序执行；GIS 依赖记录负责选择继续使用哪些文件。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)说明了检查点的线程状态保存职责。外部文件的版本检查由本项目完成。

## 3. 最小使用流程

```text
搜索并了解具体 QGIS 工具
  → prepare_workflow_step：登记本步骤
  → 调用具体 QGIS 工具或 run_python_script
  → 按需读取数据、执行自检
  → finish_workflow_step：封存执行结果及检查证据
  → 继续下一步骤
```

prepare、finish 和 fork 各自单独调用。一个 Session 同时最多保留一个尚未收尾的步骤，避免模型一次提交多个操作时混淆归属。

步骤粒度为“一次主要 GIS 调用及其自检”。多次处理需要分别登记；已经包含多个处理的大脚本可以先整体登记。

普通问答和已有工具接口继续可用。未登记的执行保留现有记录，局部复用只覆盖实际登记的步骤。验证与制图子 Agent 初期继续使用各自现有流程。

## 4. 记录哪些数据

### 4.1 工作流与分支

一个 workflow_id 对应当前用户任务。首次 prepare 自动建立 main 分支，并固定用户要求的来源与内容哈希。

| 记录 | 必要字段 |
| --- | --- |
| Workflow | workflow_id、所属 Session、本轮用户来源、记录格式版本 |
| Branch | branch_id、父分支、修正起点、理由、问题证据、继承步骤、待重算步骤 |
| StepRequest | step_id、目标、上游步骤、输入清单、预定输出、主要工具名 |
| StepExecution | 真实 tool_call_id、调用参数、工具与环境版本、执行结果引用、产物哈希 |
| StepResult | 执行状态、自检和独立复核引用、检查范围、封存记录哈希 |

step_id 表示逻辑步骤，如 project、buffer、overlay。一个实际节点由 workflow_id、branch_id、step_id 共同确定，例如 roads/main/buffer。

步骤关联使用 tool_call_id、对应消息内容哈希和外置结果资产哈希。父 Session 可以继续追加消息，已有步骤的调用身份保持稳定。完整 Session 文件的 record_hash 继续用于当前 LangGraph 检查点核对。

同一逻辑步骤修正后产生新节点 roads/fix_buffer/buffer。继承的 project 仍指向 roads/main/project。

首次 prepare 确定 main，之后只有成功的 fork 改变当前分支。prepare 只向当前分支登记步骤，历史请求的重复读取保持当前分支不变。分支状态从真实 Session 调用重建，持久化文件无需再维护一份可变的“当前分支指针”。

工作流先覆盖一次用户任务。新的用户要求重新建立 workflow_id。跨任务复用暂不建立缓存机制。

### 4.2 输入与输出身份

输入需要同时记录数据源和物理文件。GeoPackage 保留完整 source，包括图层名；同一文件内不同图层的选择进入实际参数。

版本检查采用以下规则：

- 普通文件记录绝对路径、大小和 SHA-256。内容哈希作为版本依据。
- Shapefile 检查 shp、shx、dbf，并记录已有 prj、cpg 和其他同名组成文件。重新检查时也核对组成文件集合。
- GeoPackage 按整个文件核对。写入必须完成并关闭连接；存在活动 WAL 时拒绝封存。
- 脚本同时登记主脚本、导入的本地辅助模块、配置和其他实际依赖。程序保留原有脚本与日志快照。
- 栅格的伴随文件、工程的外部图层和样式需要显式提交；首轮可回退示例使用单文件数据，控制依赖范围。

路径处理使用 pathlib。文件数据源与带图层选择的 source 分开解析。数据库连接串和访问令牌不写入工作流记录。首轮复用仅接受本地数据源。

步骤输出由 prepare 分配到独立目录。QGIS 工具的输出参数填写返回的实际路径。流程中间结果使用落盘文件。

```text
outputs/<session>/workflows/<workflow_id>/<branch_id>/<step_id>/
```

旧成果按约定只读，新分支通过引用使用旧成果。现有脚本具备文件读写能力，因此边界检查仍需在执行后和复用前再次进行。

### 4.3 执行身份

封存信息至少包括实际工具名、算法 ID、实际参数、QGIS 版本、算法帮助定义哈希、启动器路径和哈希，以及脚本与显式资源的哈希。

native 算法使用当前帮助定义核对参数默认值。脚本依赖和运行配置纳入版本。涉及插件、额外 Python 库、随机过程或外部服务时，需要明确版本及确定性；缺少这些信息的步骤标记为不可复用。

分支继承直接使用已封存的节点引用。调用参数保留真实值和绝对路径。新执行分配新的输出目录。

这些记录保护已声明的依赖。程序无法自动识别任意脚本在运行时读取的全部外部文件；这部分由执行者提交清单，并在复核中说明范围。

## 5. 四个工作流工具

### 5.1 prepare_workflow_step

建议参数：

| 参数 | 含义 |
| --- | --- |
| workflow_id、branch_id、step_id | 工作流、当前分支和本步骤标识 |
| goal | 本步骤要完成的具体目标 |
| source_indices | 相关用户原话，包含本轮最新要求 |
| depends_on | 上游逻辑 step_id 列表 |
| inputs | 数据源、脚本、配置等输入清单 |
| outputs | 输出名称到相对文件名的映射 |
| tool_name | 本步骤主要调用的具体 QGIS 工具或 run_python_script |

例如 buffer 的 outputs 为 OUTPUT → buffer.gpkg。工具返回绝对路径、上游实际节点引用和输入版本。

程序完成以下检查：

1. 标识与路径有效，当前没有其他未收尾步骤。
2. 上游属于当前分支可使用的节点，执行完成且文件版本有效。
3. depends_on 解析为确定的实际节点，引用的数据文件已进入 inputs。
4. 新步骤只依赖已完成的上游，拒绝自身依赖与循环。
5. 输出目录与已有输入分离，目标文件尚不存在。
6. 保存不可变请求，返回 ready。

工作流、分支和步骤标识只接受 1～40 个英文字母、数字、下划线或横线。outputs 的文件名必须解析到本步骤目录内。脚本先保存，再连同辅助依赖进入 inputs。

同一标识、相同请求重复调用时回读原状态。已经执行过的步骤返回实际记录，并提示继续收尾或读取结果。已有标识的目标、输入或依赖发生变化时，要求建立修正分支。

实际参数在随后的具体调用中绑定并封存。一个登记只能绑定一次主要执行。更换参数需要建立新节点。

### 5.2 finish_workflow_step

建议参数：workflow_id、branch_id、step_id、checks、verification_refs。后两项可以为空；证据不足时明确保留未检查状态。

工具从真实 Session 回读主要调用及其结果。成功路径执行以下检查：

- 调用已标记 finished，工具名与登记一致。
- 工具返回 ok=True，预定输出实际存在。脚本同时核对 returncode=0 和 script_changed=False。
- 输入在主要执行前后保持一致。
- 输出在主要执行完成后到收尾之间保持一致。
- 自检证据发生在主要执行之后，能够解析实际工具结果、脚本快照和日志版本。

checks 使用 requirement、criterion、method、coverage、status 和 evidence_indices 表达主 Agent 的自检。PASS、FAIL 需要真实工具证据，证据不足使用 UNKNOWN。检查必须说明核对了哪些输出。

verification_refs 指向现有验证子任务中的 task_id 与 check_id。程序通过 SubtaskRunner.read_result 回读，保存原检查和证据版本，并核对原委派清单包含本节点实际产物及其哈希。主 Agent 负责说明检查与当前步骤的关系。

证据文件封存复用现有 tool_evidence、save_evidence。程序检查来源和版本，检查方法是否足够仍由 Agent 判断。自检与独立验证分别标记来源。

执行成功、文件完整和检查通过分别记录。主要工具成功的步骤可以封存为 completed；它的检查状态仍可能为 UNCHECKED、FAIL 或 UNKNOWN。

若真实调用明确返回失败，finish 保存 failed、错误、日志及已有文件，随后释放当前步骤。该路径允许产物不完整。存在可信完成记录的版本检查失败也按 failed 收尾；仅有 started 时保留 uncertain，继续执行第 10 节的现场处理。

封存后重复 finish 时回读原记录。修正通过 fork 建立新节点。

### 5.3 fork_workflow

建议参数：workflow_id、parent_branch、branch_id、restart_step、reason、evidence_refs。

restart_step 是首先需要修改的逻辑步骤。主 Agent 根据真实失败、数据变化或复核结果选择该位置。问题位置尚不明确时，先取证。

程序根据依赖计算：

```text
受影响步骤 = 修正起点 + 所有依赖它的下游
继承候选 = 父分支中其余已完成步骤
```

随后重新核对继承候选的输入、产物、执行环境及检查证据。缺失、变化、未检查或存在相关 FAIL / UNKNOWN 的节点不能继承，其下游也加入待重算集合。

返回 inherited、rebuild、invalid_reasons 和新分支目录。继承节点继续引用原路径，新分支只为重算步骤分配目录。

同一分支 ID 绑定相同请求，重复调用回读原记录。存在未确认的执行时拒绝 fork，先处理现场。尚未启动主要调用的 prepared 步骤可以作为修正起点；fork 将其保留为旧分支的未执行请求，并释放登记。

首轮修正保留逻辑步骤及依赖拓扑，允许更换算法、参数和脚本实现。这样能够直接判断哪些旧步骤需要重算。

### 5.4 read_workflow

建议参数：workflow_id、branch_id、step_id、offset、limit。后四项按需填写。

默认返回当前分支的步骤摘要、继承来源、待重算项、检查范围和当前文件有效性。指定 step_id 后分段读取详细执行与证据。

工具只读已有记录和文件。默认摘要控制长度，完整参数和日志通过记录路径读取。该工具加入 PASSIVE_TOOLS。

## 6. 在工具执行处绑定真实步骤

Agent.tools 增加可选 WorkflowRunner。主任务由 application 显式注入，验证和制图子任务初期保持原有组装。

每次具体工具调用沿用以下顺序：

1. 解析参数并检查本轮可用工具。
2. 保存 Session 中已有的 started 标记。
3. WorkflowRunner 在存在待执行步骤时核对工具名、实际输入、输入版本和预定输出路径，并保存执行意图。
4. 调用现有 registry.execute。
5. 记录执行结果、输入输出版本和实际调用身份，给返回值附加 workflow 记录引用。
6. 沿用原流程保存工具结果、更新 Session 和 LangGraph 检查点。

本版为工作流控制工具增加单独调用检查。一个步骤只允许一次主要执行，同一批包含多个主要 GIS 调用时返回明确错误。

QGIS 输出按照 outputs 中的参数名核对绝对路径。脚本输出根据登记清单核对。脚本的真实读写能力沿用现状，工作流边界提供版本检查。

QGIS 的可识别输入参数按帮助定义解析，实际 source 需要包含在 inputs 中，并与登记的上游文件匹配。无法覆盖输入依赖的调用保留执行记录，其复用资格保持关闭。

主要执行之后可以读取成果并运行自检。后续脚本作为检查证据保存，封存时再次检查主要输出未被这些调用改写。需要修改成果时建立修正分支。

已有工具返回值只附加 workflow 字段。Tool、ToolRegistry、QGISClient 和现有函数签名保持稳定。项目级异常继续保留原有可观察性；执行状态不明时保留 started 记录。

Agent.model 在现有 business 上下文中加入短摘要：workflow_id、当前 branch_id、未收尾步骤和 rebuild。摘要从持久化记录重建，RunState 无需再保存一份业务图。

## 7. 状态与复用条件

### 7.1 分开保存执行和检查状态

| 维度 | 状态 | 含义 |
| --- | --- | --- |
| 执行 | prepared | 已登记，尚未调用主要工具 |
| 执行 | running | 已写执行意图，尚无可信的完成记录 |
| 执行 | executed | 主要调用成功，等待收尾 |
| 执行 | completed | 输出和记录已封存 |
| 执行 | failed | 已确认工具失败或版本检查失败 |
| 检查 | UNCHECKED / PASS / FAIL / UNKNOWN | 当前步骤实际检查结论及范围 |
| 当前有效性 | valid / stale / uncertain | 当前文件、证据与记录能否确认一致 |

stale 和 uncertain 由当前读取状态得出，历史结果继续保留。继承关系通过 reused_from 指向原节点，原节点的执行状态保持不变。

### 7.2 复用需要同时满足

1. 节点完成封存，有真实主要调用记录。
2. 原输入及完整组成文件集合保持一致。
3. 上游仍指向原版本，整个依赖闭包有效。
4. 实际参数、算法定义、环境及显式脚本依赖保持原版本。
5. 所有产物和证据文件仍存在且哈希一致。
6. 至少有一项针对输出的有效 PASS 自检或独立复核，相关已登记检查没有 FAIL / UNKNOWN。
7. 当前问题和新分支的改动没有否定该节点的适用条件。

程序判断 1～6 的结构、身份和版本。第 7 项及检查覆盖是否充分由主 Agent 判断，并写入继承理由。存在疑问时补查或重算。

PASS 的范围随证据保留。例如“CRS 与要素数量检查通过”只支持这两个判断。执行缓存不能证明整个 GIS 方法正确。

每一步无需委派独立验证。主 Agent 可使用现有 inspect_data 或小型检查脚本自检；独立验证继续选择少量重难点。缺少可用检查的步骤可以正常记录，但在新分支中需要补充依据或重算。

## 8. 完整修正示例

用户要求：道路重投影到 EPSG:32650，做 500 米缓冲，再与行政区叠加。

```text
main/project ──→ main/buffer ──→ main/overlay
     │              误用 50 米
     │
     └────────→ fix_buffer/buffer ──→ fix_buffer/overlay
                    改用 500 米
```

1. 主 Agent 搜索具体算法，登记并执行 project。自检确认 CRS、数量和输出可读，封存对应证据。
2. 主 Agent 登记 buffer，实际参数误用 50。工具正常退出，实际参数与产物均进入记录。
3. 主 Agent 执行 overlay，整理首个候选。
4. 独立验证选择距离这个重点，发现结果与 500 米要求不符，返回 FAIL 与证据。
5. 主 Agent 将问题定位到 main/buffer，调用 fork，提供检查引用和修正理由。
6. 程序重新核对 project，继承其原节点；buffer、overlay 进入 rebuild。
7. 主 Agent 在新分支调用具体 buffer 工具，使用 500 米，并完成自检。
8. overlay 的上游逻辑 ID 自动解析到新 buffer，填写新输入路径后重新执行。
9. 主 Agent 生成新候选，沿用 V7.5 的 previous_id、repairs 和独立复查。

底层复用依据为实际引用与文件版本。fork 返回待重算集合，主 Agent 继续调度具体调用。

## 9. 与 V7.5、V7.6 的衔接

### 9.1 验证定位

验证子任务接收封存的工作流清单及相关文件，通过现有 artifacts 参数传入。清单帮助它查看实际算法、参数与上游。

验证结果继续使用 check_id、finding、evidence。提示词要求 finding 尽量写明有关的逻辑步骤。回退位置由主 Agent 结合这些信息选择，程序核对节点确实存在。

本版继续使用当前检查协议。地图观察保留 map_notes。视觉意见可用于新制图简报，数据依赖失效按步骤记录处理。

### 9.2 候选与最终交付

review_delivery 增加可选 workflow_ref，默认 None，已有调用保持有效。其内容包含 workflow_id、branch_id 和本候选使用的步骤引用。

使用工作流的候选需要：

- 提交当前最新分支的引用，并覆盖实际使用的步骤依赖。
- 将封存工作流清单写入候选目录，作为输入交给验证 Agent。
- 记录交付文件与步骤产物的对应关系。直接复制的数据核对哈希；后续制图等派生成果登记其输入版本。
- 确认 rebuild 中原定的修正和下游步骤已经完成。

application 组合工作流检查与原有 delivery.check。交付前检查工作流引用、依赖文件和候选版本，再执行原有重点复核条件。

历史步骤检查只支持继承判断。新候选继续执行当前 V7.5 复核流程，检查范围仍为 selected_risks。

### 9.3 制图和子任务

分析结果变化后，用新 cartography task_id 和新候选进行制图。保持现有 brief、设计文件、字体、manifest 和整图读取要求。

首轮不把子 Agent 的内部工具调用展开到主工作流。输入指纹变化由现有 SubtaskRunner 检出，主任务据此重新委派。

## 10. 恢复与失败处理

| 中断位置 | 恢复方式 |
| --- | --- |
| prepare 后，主要工具尚未启动 | 核对原请求与输入后继续原步骤 |
| 主要工具已完成并保存结果，尚未 finish | 回读真实调用及输出版本，继续自检和收尾 |
| 仅有 started，无法确认工具是否完成 | 标记 uncertain，保留文件和日志，停止该步骤的自动重放 |
| finish 已封存，返回或恢复时重复调用 | 相同请求回读原记录 |
| 输入、输出或证据变化 | 显示 stale 及具体差异，建立修正分支 |
| Session 与 LangGraph 检查点不一致 | 沿用当前阻止自动重放的处理，检查现场后再恢复 |

Session、工作流文件和外部 QGIS 进程之间存在独立写入边界。原型采用执行前记录意图、执行后保存结果、重复调用回读的方式，降低重复执行风险。

状态未知时，不根据文件存在推断执行成功。已有完成记录且 Session 一致时，可以重建缺失的派生索引；涉及 Session 与检查点冲突时仍按现有恢复要求处理。

新分支使用新目录，失败输出留在原位置。初期提供清楚的现场与恢复提示。无法确认的步骤由用户检查后处理。

## 11. 项目结构和修改范围

```text
gis_agent/
├─ core/
│  └─ workflow.py             新增：步骤数据、依赖闭包和继承资格判断
├─ persistence/
│  └─ workflow.py             新增：请求、执行和封存记录的读写与哈希核对
├─ agents/
│  ├─ workflow.py             新增：WorkflowRunner，组合文件记录与真实调用
│  └─ delivery.py             保存可选 workflow_ref，冻结候选工作流清单
├─ tools/
│  ├─ workflow.py             新增：四个工具的参数和薄封装
│  └─ delivery.py             增加可选参数，默认行为保持原状
├─ agent.py                   注入可选 runner，绑定工具调用，提供短摘要与批次检查
├─ application.py             组装主任务 runner，组合交付检查
└─ prompts/
   ├─ workflow.j2             新增：登记、收尾、定位与修正的短说明
   ├─ system.j2               按主任务能力引入说明
   └─ verifier.j2             通过实际参数与依赖辅助定位问题

sessions/<session>.workflows/<workflow_id>/
├─ workflow.json
└─ branches/<branch_id>/
   ├─ request.json
   └─ steps/<step_id>/
      ├─ request.json
      ├─ execution.json
      └─ result.json

outputs/<session>/
├─ workflows/<workflow_id>/<branch_id>/<step_id>/
└─ candidates/<candidate_id>/
   └─ workflow.json             当前候选使用的封存清单
```

core 使用少量 dataclass 表达 StepRef、StepRequest、FileVersion 等数据，计算上游、下游和继承集合。持久化模块复用 write_json、file_digest 和已有证据函数。WorkflowRunner 负责顺序编排，tools 只负责暴露调用接口。

execution.json 在执行阶段记录 started 与结果，result.json 在收尾时封存。记录路径与哈希随工具结果进入 Session。读取时相互核对，派生摘要可以重建。

输出根目录使用现有配置，新增文件都通过 Session 与 output_dir 定位。V8.0 无需新增第三方依赖，也无需新增一套存储服务。

Agent 新增可选依赖，已有构造方默认 None。review_delivery 的新参数默认 None。实施时同步检查 application、子任务创建处和测试中的构造方。

## 12. 开发顺序与验收

### 第一阶段：记录一个真实步骤

实现文件身份、prepare、主要调用绑定、finish、read。先用真实 QGIS 完成一次重投影，检查记录能对应实际工具、脚本和文件。

### 第二阶段：完成一次局部修正

实现依赖闭包、fork 和版本继承。用固定三步流程主动设置错误距离，再改正。该实验验证回退机制，模型发现错误的能力另行评测。

### 第三阶段：接入复核与交付

将问题证据、workflow_ref 和候选清单接到现有 V7.5。确认旧候选不能覆盖新分支的交付状态。制图继续复用 V7.6。

### 验收点

| 场景 | 应观察到的结果 |
| --- | --- |
| 缓冲参数错误 | 新分支只重新执行缓冲和叠加，重投影工具实际调用次数为 1 |
| 上游输入改变 | 原节点及其依赖不能继续继承，返回具体失效原因 |
| Shapefile 的 dbf、prj 或组成集合变化 | 输入版本变化被检出 |
| 产物或证据删除、改写 | 复用及交付检查返回 stale |
| 修改算法、脚本或显式辅助资源 | 新节点执行，旧记录保持原版本 |
| 只有成功退出，缺少有效检查 | 可以记录执行成功，继承时返回检查不足 |
| 工具失败或仅有 started | 保留现场，恢复不会再次自动提交该操作 |
| 重复 prepare、finish、fork | 回读相同记录，GIS 调用次数没有增加 |
| 两条流程共享上游 | 修正只沿实际依赖传播，无关分支仍可继承 |
| SQLite 重开并继续 | 分支、步骤和真实 Session 调用保持对应 |
| 修改后仍尝试提交旧候选 | 工作流与候选检查要求提交当前分支 |

实现阶段先以 pytest 和真实本地 QGIS 检查核心失败点。文档设计阶段不执行这些测试，也不调用实际模型 API。

## 13. 成本与 V7 收尾评测

登记和收尾会增加工具调用及消息。大文件哈希也有本地 I/O 成本，因此局部复用的收益需要测量。

本版先限定单任务、少量步骤。每个核对边界对同一路径只算一次哈希，供该次依赖闭包检查复用；下一次边界重新读取内容。工作流完整记录落盘，上下文只携带当前分支摘要。

V7 收尾使用相同模型、任务与可比预算，对照当前流程、重点验证流程，以及工作流局部修正流程。分别统计：

- 最终正确率和实际复核范围。
- 错误定位是否准确。
- 各 GIS 步骤实际运行次数及复用次数。
- 登记、版本核对、修正和重算各自耗时。
- 主任务、验证和制图的总 token 与 API 成本。

同时保留不出错的短任务，测量新增机制的额外开销。长流程或昂贵上游发生局部错误时，再观察重复计算是否减少。

V8.0 的交付物为一个可追溯、可恢复、能保留有效上游的局部修正原型。完成真实评测后，再决定后续版本如何扩展分支选择与搜索。
