## 一、为什么不用重型 DAG，而是“产物自动体征 + 双栈分级 Skills”？

### 1.1 来自本库 V8 实验与 2026 顶会 Benchmark 的双重证据
- **显式 DAG / 重放工具在自由 Code Agent 中收益极低**：V8.0/V8.1 已验证完整的 `local_replay` 与依赖图（[v8.1-implementation-report.md](v8.1-implementation-report.md)），但在 GeoAgentBench 53 题 2601 轮实测中主动调用次数为 **`0`**；相反，在方案 A 第 `09` 题中，模型通过普通 Python 将阶段产物存盘并在超时后读取改写分块算法，直接自然复用了上游成果。
- **GIS Agent 真正的头号失分根因**：根据 *GISAgentBench (2026)* 轨迹统计与本库 53 题复盘，核心败因集中在：
  1. **缺漏关键前置操作（约 28.3%）与顺序错乱（约 18.4%）**：如未重投影、未修无效几何直接叠加、未对齐像元网格、未按 `scale/offset` 定标直接计算 `SAVI`；
  2. **静默算错向下游传播**：脚本退出码为 `0` 且文件非空，但结果全 `NaN`、`-9999` 混入均值、连接后要素归零或翻倍；
  3. **环境库缺失引发的手搓劣化**：在缺少 `pykrige`/`libpysal`/`sklearn`/`rasterstats` 的环境中被迫现写几百行野生插值与随机森林，而在**已经装齐 `uv` 科学库的环境下却因旧 Skill 索引模糊、缺少激活线索而仍去自造轮子**。

### 1.2 三端部署下“Python 科学库差异”的核心裁决
您指出的关键现实矛盾必须正面解决：
- **QGIS 插件端（`qgis_plugin`）**：直接寄生于用户本机原装 QGIS Python（仅有 `qgis`, `geopandas`, `pyogrio`, `rasterio`, `shapely`, `scipy`, `numpy`, `pandas`, `matplotlib`, `networkx`），**绝不能假定用户装过 `pykrige` / `libpysal` / `esda` / `scikit-learn` / `duckdb` / `netCDF4`**；
- **独立桌面 `.exe`（`desktop_studio`）与 Harness 插件（`harness_plugin`）**：由 `uv`（`pyproject.toml[geo]`）直接携带全套 42 个满血空间科学计算库，**应当优先一两行直接调用权威库**，避免低效手搓与数值偏差。

**解决方案：双栈分层能力披露（Tier A 核心通用栈 + Tier B `uv` 扩展加速栈）+ 运行时自动探测注入**。绝不写两套互相矛盾的 Skill，也不对 QGIS 插件端撒谎。

## 二、模块 1：执行器零轮次「新产物空间体征回执」（Auto Vital Signs）

### 2.1 设计边界
- **只报客观物理事实，绝不作业务对错裁判**（严守通用性底线：不判断“500 米缓冲合不合理”，只报告“生成了什么 CRS、几个要素、几个无效几何、有效像元占比与真实 min/max”）。
- **零额外模型轮次**：直接随 `run_python_script` 与 `run_qgis_algorithm` 的返还结果 `outputs` 附带，不新增任何 Agent Tool。
- **有界开销防御**：每次调用最多对前 **3 个**新产出或被修改的空间文件（`.tif/.tiff/.img/.gpkg/.shp/.geojson`）做头信息与缩略抽样；单次附加探测总预算控制在 `<= 150ms`（仅读文件头 + 至多 `256×256` 概览窗口或前 200 个矢量几何有效性抽样），超时或非空间文件静默跳过并保留基础 `bytes` 字段。

### 2.2 具体接口与数据格式
新增轻量函数 `summarize_spatial_outputs(outputs: list[dict[str, Any]], launcher: Path | None = None)`（置于 `gis_agent/runtime/inspect_fast.py` 并提供进程内直接调用 + 跨解释器回退双通道）：
- 若宿主解释器（如 `uv .venv`）自身已安装 `pyogrio` 与 `rasterio`，直接在主进程内存毫秒级提取，无需额外拉起子进程；
- 若宿主为极简核心环境而 GIS 库在外部 `python_launcher` 中，仅当存在新空间文件时以 `--batch` 单次调用 `inspect_fast.py` 批量读取（或由 `inspect_fast` 跳过不支持格式）。

产出条目结构示例（嵌入现有 `outputs[i]["spatial"]`，不破坏现有字段兼容）：
```json
{
  "path": "E:/.../output/roads_buffer.gpkg",
  "exists": true,
  "bytes": 1843200,
  "empty": false,
  "spatial": {
    "kind": "vector",
    "crs": "EPSG:5880",
    "units": "metre",
    "feature_count": 12,
    "geometry_type": "MultiPolygon",
    "invalid_sample_count": 0
  }
}
```
栅格示例：
```json
{
  "spatial": {
    "kind": "raster",
    "crs": "EPSG:32612",
    "units": "metre",
    "shape": [4096, 4096],
    "dtype": "float32",
    "nodata": null,
    "scale": 1.0,
    "valid_ratio": 0.964,
    "raw_min": -0.312,
    "raw_max": 0.845
  }
}
```
若脚本算完出现 `feature_count == 0`、`valid_ratio == 0.0`、`invalid_sample_count > 0` 或意外 `units == "degree"`，模型在当轮 `tool` 返回里立刻看到异常，**0 额外轮次直接原地修脚本或重算**。

## 三、模块 2：运行时环境双栈探测自动注入（破解 QGIS vs `uv` 差异）

### 3.1 设计机制
1. **`probe_launcher` 缓存指纹**（`gis_agent/runtime/probe.py`）：
   - 按 `launcher.resolve()` 缓存当次会话的库探测结果（仅在会话首轮探测 1 次，耗时 `< 0.5s`）。
   - 返回精简 `runtime_capabilities`（`< 50` Token）：
     ```json
     {
       "mode": "uv_standalone", // 或 "qgis_plugin" / "dual"
       "has_qgis": false,
       "tier_b_available": ["duckdb", "esda", "libpysal", "mapclassify", "netCDF4", "pykrige", "rasterstats", "scikit-learn"]
     }
     ```
2. **注入位置不破坏 KV Cache**：
   - 随 [agent.py](gis_agent/agent.py) 中本就位于历史列表**最末尾**的 `business["runtime_capabilities"]` 传入（动态尾部设计，前置历史前缀缓存 100% 不受影响）。
3. **可选双解释器协同（桌面/CLI 本机同时存在 QGIS 与 `uv` 时）**：
   - `AppConfig` 维持现有单 `python_launcher` 主配置向后兼容；同时当配置 `GIS_AGENT_QGIS_DIR` 且当前运行于 `uv` `.venv` 时，在 `runtime_capabilities` 标注可用能力边界：需要标准 QGIS/GRASS 算法时调 `run_qgis_algorithm`，需要 `pykrige`/`sklearn`/`libpysal` 时在 `.venv` 下跑 `run_python_script`。

## 四、模块 3：遵照 Anthropic 与 OpenAI 官方指南的 Skills 重构与写法规范

综合检索并遵循以下两份权威指南，彻底解决当前 `gis-spatial-analysis` “单文件臃肿、触发率仅 14/53”的问题：

### 4.1 提炼后的官方写作七条铁律（Anthropic + OpenAI 合一规范）
1. **技能总量严格控制在 10 个以内（推荐 6～7 个正交领域）**：数量过多会导致元信息互相挤压、路由混乱；过少（当前仅 3 个）则会导致空间分析描述过于宽泛、命中率低。
2. **三层渐进式披露（Progressive Disclosure）**：
   - **L1 元数据（常驻 System Prompt）**：仅放 `name` 与精准 `description`（总长 `< 1024` 字符）。
   - **L2 核心手册（`SKILL.md`）**：按需加载；正文必须 **严格控制在一屏/轻量内（目标 `50–150` 行，硬上限 `< 500` 行）**，只给决策树、关键防坑与导航表，绝不塞满屏幕的 API 文档。
   - **L3 深度参考与可执行样板（`references/` + `scripts/`）**：只保留**单层深度链接**（直接从 `SKILL.md` 指到 `references/xxx.md` 或 `scripts/yyy.py`，禁止参考文件之间互相嵌套深跳），且按条件引导阅读（例如 `"Read references/hydrology-d8.md when extracting streams or basins."`）。
3. **`description` 的 High-Trigger 写法（OpenAI Codex 规范）**：
   - 使用 **第三人称陈述 + 动作动词开头**，前置核心领域名词与报错关键词；
   - 明确写清 **"What it does" + "Use when ..." + "Do not use for ..."（负向排除边界，防跨 Skill 误触）**。
4. **`name` 命名规范（Agentskills.io 规范）**：小写字母 + 数字 + 连字符（`[a-z0-9-]+`），目录名与 `name` 完全一致，保留全英文内容以保证分词紧凑与 `test_v7911_skills.py` 检查通过。
5. **只写“能弥合真实失败”的程序性知识（Eval-Driven）**：不教基础 `import pandas`，重点写清真题实测暴露的高频陷阱（如 `SAVI` 尺度、GRASS 负号汇流累积、一对多连接膨胀、非嵌套 CV 泄漏）。
6. **双栈环境诚实分流（Tier A vs Tier B）**：每个分析 Skill 明确写清 **通用核心实现（QGIS 原装 Python 可用）** 与 **科学扩展实现（当 `tier_b_available` 含对应包时选用）**，杜绝模型在纯 QGIS 插件里盲调缺失库报错。
7. **自带零依赖可验证反例脚本**：每个高风险机制继续配套 `< 100` 行的独立 `.py` 样板脚本，离线 `pytest` 直接实机跑通。
