## 3. 状态与接口

| 状态 | 业务含义 | 后续处理 |
| --- | --- | --- |
| answer | 普通问答完成 | 可以开始另一轮 |
| completed | 所需工作完成，不能有unresolved | 正常结束 |
| partial | 有可靠部分成果，仍有尚未满足要求 | summary说明范围，unresolved列缺口；有文件时列artifacts |
| needs_input | 缺少必要输入或关键决策，需要用户回答 | question明确缺什么、影响及用户可提供内容 |
| blocked | 暂时没有可靠继续方法 | 说明阻碍与未知，不标成功 |
| cancelled | 用户主动取消 | 由客户端cancel产生，保留现有成果 |

cancelled 不作为模型可选状态暴露。客户端显式取消提供确定的用户意图，模型无法自行将困难任务标为用户取消。CLI目前使用 `cancel` 命令；自然语言取消意图识别留给后续交互设计。

question 必须为非空文字。reason可选，值为 missing_input、business_decision、data_quality、unsupported、capability_limit。普通代码异常属于可恢复诊断，不能作为业务停止原因枚举直接提交。字段不能自动判断这个专业分类是否正确。

partial 可以是有用的文字结果，不强迫生成无意义文件。已有文件的路径仍需真实存在。completed 和未完成计划、unresolved 的矛盾仍会被拒绝。partial/blocked/needs_input 会带上真实 unfinished_plan，但不会把计划未完成项擅自改为已完成。

已有 needs_input 历史不需要迁移。旧记录没有 question 时，CLI显示旧 summary。新请求使用新校验。原始 Session、工具结果和哈希保持原样。

## 4. 等待与恢复的真实机制

### 4.1 业务等待与图状态

本轮继续使用已有 finish_task(needs_input)。它完成当前工具批次，再经原 finish 节点保存最终记录，图到达END。**业务任务仍在等待用户，END只说明这一轮工具循环安全结束。**

LangGraph原有 interrupt_after=['tools'] 继续作为内部检查点。它与业务等待分开。若进程停在内部检查点，先沿用原resume完成该批次；确认图没有待运行节点后才能接受新回答。

这样不需要在可能重入的计算节点内部新增 interrupt，也不回放过去模型决策。等待问题从实际 finish_task 工具结果派生，request_id优先使用真实execution_id，旧记录用稳定消息位置回退。

### 4.2 用户回答

```python
conversation.waiting
conversation.reply(text, request_id=question_id, reply_id=client_message_id)
conversation.send(text)  # 等待中自动关联为回答
```

回答作为真实用户消息保存，带 in_reply_to 和 reply_id。没有更改旧消息、插入虚构工具结果或新建Session。普通文本、文件路径、参数和批准范围都由模型结合任务读取和解释。

回复前核对当前磁盘记录、会话快照及record_hash。空回复、过期request_id、重复reply_id和正在执行的图会拒绝。不同客户端已经改变记录时要求重开，避免覆盖。当前仍按单Session单写者使用；没有新增多客户端并发锁。

继续采用当前对话和已取得知识。已有计划、历史、产物及摘要继续可见；已发现QGIS算法保留到回答轮次。Harness不自动再运行已完成工具，但模型仍可按新信息决定重算。它无法保证模型永远不主动重复计算。

### 4.3 两个持久化窗口

**回答已保存、首个模型节点尚未开始：** 仅当记录恰好比原needs_input终态多一条关联用户回答，且前缀哈希和request_id准确一致，continue_answer才开始新轮次。其他偏差拒绝。若图已在运行中，则走原检查点resume保护。

**取消已保存、检查点更新失败：** 只允许原等待记录之后多一个匹配的用户取消事件。核对旧前缀哈希与问题ID后，通过正式graph.update_state(as_node='finish')补齐终态。篡改历史、来源不符或不确定执行仍被拒绝。

没有操作SQLite内部表，没有统一忽略record_hash，也没有放宽V8.1未知副作用的恢复限制。

## 5. CLI 用法

```powershell
python main.py --session analysis-01 chat
python main.py --session analysis-01 waiting
```

运行至needs_input后，CLI显示summary、question、未完成事项和已有artifacts。

- 直接输入补充内容：在原Session继续。
- 输入exit，或在输入提示处EOF/Ctrl+C：保留等待并退出。
- 再用同一Session打开：展示原问题，不自动请求模型。
- 等待时输入cancel：保存用户取消事件及成果，不调用模型。
- 回答仍不足：模型可提出下一问题，使用新的request_id；旧回答保持可追溯。

waiting 命令只读记录，不需要模型API Key，也不启动QGIS。chat仍使用原运行环境和Key配置，真正继续解题会请求模型。原生计算执行中不支持任意内存暂停；运行中强行中断仍受原执行标记和恢复约束保护。

## 6. 能力边界怎样处理

程序负责结构和执行语义。专业判断继续由单Agent结合事实完成：

| 情况 | 指导与可用机制 |
| --- | --- |
| 可发现的文件名、图层或CRS | 先用现有目录、元数据、Skills，不直接询问 |
| 普通代码或接口错误 | 原编辑、执行、历史和重放路径继续可用 |
| 非必要数据缺失 | 继续可靠部分，说明结果范围 |
| 必要人口、输入或关键决策缺失 | needs_input明确请求，或partial保留独立成果 |
| 道路断开、人口无接收对象 | 保留不可达/未分配，不补造事实；复用V8.3资产 |
| 方法、环境或能力限制 | 合理替代后仍无法可靠继续时blocked/partial |
| 无新诊断的重复失败 | 换方法或停止受影响部分，说明阻碍 |

没有全局硬编码“失败N次就停”。同一工具参数在代码修改后重试可能合理。本轮不新增启发式GIS规则引擎，不把stderr当作专业能力证明，也不按读取工具次数强制确认。

System和Verification Skill明确了缺口与业务结论的区别。实际道路拓扑、坐标解释和业务政策仍需证据。结构校验能拒绝矛盾状态，不能普遍识别所有静默错误或编造陈述。

独立可完成的工作应在提问前尽量完成。等待之后当前单Agent轮次停止，不会在后台自动调度其他分支。这是V8.4边界，未引入分支调度器。

## 8. 完整跨进程例子

固定回复示例使用真实文件与两个独立宿主进程，属于协议验证：

1. 原输入：计算前段基值，再根据缺少的乘数给出最终结果。
2. 第一个进程实际写入prefix.json，value=6。
3. Agent工具提问：`What multiplier should this task use? The final value depends on it.`
4. 状态needs_input，artifacts列prefix.json，unresolved说明乘数及最终结果。Session与SQLite保存后进程退出。
5. 第二个进程重开相同Session/thread。用户回答：`Use factor 7 for this task`。
6. 回答带原问题ID，只执行后段，生成result.json：`{"value":42}`。
7. 状态completed。前段函数设置了重复启动即失败的保护，测试没有触发它。

完整记录在example/：两个阶段的结果、原Session、工具资产、checkpoint.sqlite、prefix.json、result.json和processes.json均保留。真实GIS版本另在pytest证据中覆盖。

这个例子验证实际生产入口的提问、退出、关联回答与继续能力。自然模型识别未知条件的行为仍需后续实测。

## 9. 开销与普通任务

没有增加Agent工具。新增两个可选finish_task字段和业务状态。使用本机实际tokenizer，对比08ddd57的同一System、Skill索引和计划Schema：1457→1654 token，增量197 token。图像和Memory条件保持一致，其他工具未计入差值。

等待问题派生查询在一万条内存前缀记录后的中位数约0.0042毫秒、p95约0.0064毫秒。它只解析末尾必要结果，无全盘文件扫描。回答边界核对仍会读取Session和检查点，长记录的磁盘开销需在真实长任务中继续测量。

正常固定任务仍是2次模型回复、1次工具执行。等待不轮询模型，查看问题、退出和取消不增加模型调用。用户回答后会正常开始一个模型轮次，这是继续解题所需请求。实际模型可能增加或减少提问，本轮无法测得净Token与成功率收益。

## 11. 兼容性、边界与V9

- Checkpoint继续使用原810；旧790和原哈希保护不普遍放行。
- 原始历史不改写，没有复制一套任务存储。
- Memory仍按原成功结束策略维护；等待不会被当作成功触发末尾记忆提取。
- local_replay继续可选，受控文件身份、冻结代码、并发锁和未知结果处理保持。
- 回复只做非空和来源检查。文件内容、人口合法性和业务选择是否足够由模型按事实核查。
- 单Session按单写者使用；读后同时写的竞争没有升级为多客户端事务。
- 运行中工具与Python内存不能任意暂停或回滚；不确定副作用仍需保留现场。
- 程序不能保证模型不造假、不重复尝试或一定知道何时提问。当前交付是可用机制、指导与免费协议证据。

V9仍需完善：GUI问题展示、文件选择、结构化选择与输入校验、多客户端提交、问题过期、运行中取消、后台任务、独立分支继续和自然语言取消意图。专业模型行为需要新预算下的自然任务对照，不能用固定回复通过率替代。
